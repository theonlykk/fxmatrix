# ADR-109: SRE Entry-Pending-Order Sweep on Reconstruction Success

## Status

Accepted — implemented locally, Tier 1 605/613 (+9 new tests, all pass; 8 authorized Cases 3/5 reds unchanged per ADR-108 Problem 3). DeepSeek narrow sweep audit: SAFE. Gemini architectural clearance and execution mandate: 2026-08-11.

## Context

Tier 2 live drill (Drill A) found that after crash recovery, SRE correctly reconstructs positions, exit orders, and deal history — but pre-existing entry-side pending limit orders (L0/Add/Reload, entry magic) remain on the broker. The EA tick loop then places fresh quotes alongside them, producing duplicate resting orders (observed on all three production instances).

Exit-hedge orders (exit magic = entry magic + `V2_EXIT_MAGIC_OFFSET`, i.e. +2) are correctly adopted by the exit-order matcher and must NOT be swept.

DeepSeek narrow sweep audit verdict: SAFE — the sweep cannot delete orders reconstruction still needs; the re-select guard is defense-in-depth only.

## Decision

After successful SRE reconstruction on the live OnInit path (`V2_SRE_RunSideOnInit`), sweep stale entry-magic pending limit orders from the broker order pool before the EA enters its normal tick loop.

### Scope and placement

- **Live caller only:** `V2_SRE_RunSideOnInit` success path, immediately after `V2_SRE_RunOnInitSteps3To10` returns `V2_SRE_OK` and before the final `return false`.
- **NOT** in `V2_SRE_RunOnInitSteps3To10`, `fxmatrix_v2_state_reconstruction.mqh`, fixture paths, or halt paths.
- **NOT** exit-magic orders — filtered by `entry_magic`; exit magic differs by `V2_EXIT_MAGIC_OFFSET = 2`, so exit hedges are structurally unsweepable.
- Deletes via `V2_OrderSendCounted` (API-counted telemetry), not raw `OrderSend`.

### Helper: `V2_SRE_SweepEntryPendingOrders(symbol, entry_magic)`

Reverse loop over `OrdersTotal()` (descending index — safe under removal-during-iteration). An order is swept only if all of the following hold:

- ticket valid and `OrderSelect` succeeds
- `ORDER_SYMBOL == symbol`
- `ORDER_MAGIC == entry_magic`
- `ORDER_TYPE` in `{ORDER_TYPE_BUY_LIMIT, ORDER_TYPE_SELL_LIMIT}`
- resting-pending state (see guard below)

### Re-verify guard (Gemini-mandated, per DeepSeek Q4)

Immediately before delete, the order is re-selected and its state re-verified as resting-pending:

```mql5
if(!OrderSelect(ticket)) continue;
if(!V2_SRE_OrderStateIsRestingPending(OrderGetInteger(ORDER_STATE))) continue;
```

Gemini's ruling on the guard (verbatim):

> "Implement the `V2_SRE_SweepEntryPendingOrders` helper as specified in the live orchestration layer. You must include the optional re-select/verify-pending guard. In a live production environment, relying on a cached `OrderGetTicket()` loop without a secondary state verification immediately prior to `TRADE_ACTION_REMOVE` is an unnecessary risk. The defense-in-depth guard costs microseconds and prevents latent race-condition deletions."

**MQL5 note:** `ENUM_ORDER_STATE` has no `ORDER_STATE_PENDING`. Resting pool limits use `ORDER_STATE_PLACED` (and the transient `ORDER_STATE_STARTED`). `V2_SRE_OrderStateIsRestingPending()` returns true for `{ORDER_STATE_PLACED, ORDER_STATE_STARTED}` — the closest safe form, which correctly excludes `FILLED`, `PARTIAL`, and cancelled/rejected states.

### Result telemetry

`V2SREOnInitSideResult.entry_pendings_swept` — count of orders successfully removed. Initialized to 0 in `V2_SRE_ResetOnInitSideResult`.

## Known Limitations

### 1. Flat-book stale-L0 gap (out of scope for SRE — Gemini ruling)

The sweep runs only when reconstruction runs, which is gated on open positions (`V2_IsOrphanedStartupState`, `layer_count > 0`). A flat-book restart with stale L0 quotes and no open position is NOT covered by this sweep.

Gemini's ruling (verbatim):

> "Document the flat-book stale `L0` quote gap in ADR-109 as a known limitation, but do not expand the SRE footprint to fix it. The State Reconstruction Engine's mandate is to rebuild an orphaned, active book (`layer_count > 0`). A flat book is, by definition, a stateless system requiring no reconstruction. If the baseline (non-SRE) EA tick loop leaves duplicate stale `L0` limit orders on a flat restart, that is a defect in the normal quoting engine's order-management lifecycle, not a crash-recovery failure. Keep SRE tightly scoped. We will address baseline flat-book quote sweeps in a separate optimization pass if it proves to be a live issue."

### 2. `ORDER_STATE_PARTIAL` entry limits (confirmed correct behavior — Gemini ruling)

The guard intentionally skips `ORDER_STATE_PARTIAL` entry limits; the filled portion is handled by normal deal-fill logic and the unfilled remainder is left for the tick loop — a partial mid-sweep is not force-removed.

Gemini confirmed this as correct existing behavior, not a design gap: forcing `TRADE_ACTION_REMOVE` on an `ORDER_STATE_PARTIAL` limit collides with the broker's matching engine mid-execution, introducing a race condition that risks corrupting terminal state synchronization. Leaving the unfilled remainder for the standard `OnTradeTransaction` deal-fill logic is the safest, most deterministic path.

## Testing

Fixture tests added to `fxmatrix_v2_tests.mq5` (3 functions, 9 assertions):

1. Mock sweep over 7 mixed orders → `swept == 3`; exit-magic, wrong-symbol, wrong-type (`BUY_STOP`), and `FILLED` orders all correctly excluded (one negative case per filter dimension).
2. Reset defaults → `entry_pendings_swept == 0`.
3. Pure sequence + fixture halt/success paths → field stays 0 (sweep unreachable on the pure and halt paths; the success path invokes it but finds no live orders in the test harness).

Suite result: **605/613** — no regression beyond the authorized Cases 3/5 reds (pairB/pairC long HALT_30, authorized red per ADR-108 Problem 3).

Note: by construction the unit tests exercise the filter and the wiring, but not the live `TRADE_ACTION_REMOVE` path — the test branch counts, it does not delete. Live deletion is validated by the clean Drill A on a fresh account.

## Consequences

**Positive:**
- Eliminates duplicate resting entry quotes after crash recovery with an open book.
- Exit hedges untouched; API-counted deletes preserve the ping-budget telemetry.

**Negative / trade-offs:**
- Flat-book stale-quote scenario remains unaddressed (see Known Limitations 1).
- `ORDER_STATE_PARTIAL` remainder left for the tick loop (see Known Limitations 2).
- One additional broker API pass on successful reconstruction startup (bounded, small).
