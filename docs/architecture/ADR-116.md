# ADR-116: BCC v1.1 -- Observability (Print findings + clean-sweep heartbeat)

## Status

Accepted -- 2026-08-14. Log-side observability only; no change to BCC
detection, cadence, gating, or the detect-only guarantee. Follows ADR-115
(BCC v1). Committed to origin; VPS deploy deferred to the next natural
reattach window (v1 remains live and correct in the interim).

## Context

BCC v1 (ADR-115) was deployed to the VPS and, during the post-deploy
reconciliation, correctly fired a real ONE_LEGGED finding (a stacked EURUSD
long side that momentarily had no add-pending after its add order was
cancelled during the reconcile). The finding was debounced across two sweeps
and surfaced on the pipshed dashboard -- proving BCC live and its C3 check
working end to end.

However, two observability gaps surfaced when trying to confirm BCC's state
from the VPS console:

1. FINDINGS ARE TELEMETRY-ONLY. The emit path calls V2_PushSystemAlert
   (exits.mqh 280-289), which only appends the message to the telemetry
   alerts[] array -- it does NOT Print. So a BCC finding reaches pipshed but
   never the Experts log. Grepping the VPS log for `BCC |` returned nothing
   even though a finding had clearly fired (it was visible on pipshed). From
   the console, BCC findings were invisible.

2. NO HEARTBEAT ON CLEAN SWEEPS. BCC emits only on a finding; a clean sweep
   produces no line. Combined with (1), a running-and-clean BCC is
   indistinguishable in the log from a disabled or hung BCC. Liveness could
   only be confirmed by opening the EA Inputs dialog to read InpBccEnable --
   not viable for confident remote monitoring.

Net: a monitor whose "all clear" is indistinguishable from "dead" gives false
assurance. Liveness must be confirmable from the log alone.

## Decision

Two log-side additions, no detection change:

1. Print every debounced finding. At the streak>=2 emit site in
   fxmatrix_v2_bcc.mqh, add Print(msg) alongside the existing
   V2_PushSystemAlert(alerts, msg). Findings now land in BOTH the Experts log
   and the telemetry payload. V2_PushSystemAlert itself is unchanged
   (queue-only) so other callers stay quiet; the Print is added at the BCC
   call site only.

2. Per-sweep heartbeat. In V2_Bcc_MaybeRunTier3Sweep (engine.mqh), after both
   side sweeps, emit one line per sweep cycle:
   `BCC | sweep=OK | long_findings=N | short_findings=M | swept=K`
   It sits after the InpBccEnable early-return (a disabled BCC stays fully
   silent -- no false heartbeat), is emitted once per InpBccSweepSec cycle
   (not per side), and is LOG-ONLY (not pushed via V2_PushSystemAlert -- a
   60-second telemetry heartbeat would spam the pipshed alert banner).
   V2_Bcc_RunSideTier3Sweep returns an int findings-count for the heartbeat;
   this is reporting-only and does not change what it detects.

## Rationale

- Print-alongside-queue keeps the telemetry path identical (pipshed behaviour
  unchanged) while making findings visible to the console -- the cheapest fix
  that closes gap (1).
- A log-only heartbeat closes gap (2) without banner spam: liveness becomes a
  one-grep answer (`Select-String BCC | sweep=OK`) and a stale/absent
  heartbeat is now a real signal.
- Detect-only is preserved: both additions are Print (pure output); no trade
  operations added. The findings-count return is reporting-only.

## Verification

- Unit suite green; only reds are the 8 authorized ADR-108 tier1 pairB/pairC
  long HALT_30 baseline. Added: Test_BCC_Tier3SweepReturnsPendingCount and
  debounce pending-count assertions (Print is additive; existing alert-array
  assertions unaffected).
- GUI compile 0/0 across the three unified shells and the tests EA.
- Detect-only reconfirmed: no OrderDelete / PositionClose / OrderSend /
  CloseBy added; Print only.

## Consequences

Positive:
- BCC findings and liveness are both confirmable from the Experts log alone,
  on a headless VPS, without opening EA properties.
- The stale-pipshed-alert confusion from the v1 deploy (finding visible on
  pipshed, absent from log) cannot recur.

Deferred / non-goals:
- pipshed alert lifecycle (auto-clearing a resolved finding) is NOT addressed
  here. BCC still sends findings, not all-clears, so pipshed continues to
  latch the last alert until dismissed. An all-clear/resolved-signal design is
  a separate follow-up if pipshed-side auto-clear is wanted.
- VPS deploy of v1.1 is deferred to the next reattach window; v1 remains live
  and correct (its detection is unchanged) in the interim.
