# ADR-115: Book-Consistency Check (BCC) v1 -- Passive Exit-First Book Auditor

## Status

Accepted -- 2026-08-14. Detect-only observability layer, no live-path change.
Relates to: ADR-106..113 (State Reconstruction Engine -- BCC reuses its
eligibility/assignment logic), ADR-108 (HALT_30 authorized test baseline,
unchanged), ADR-114 (V2.5 carry-corrected exits -- BCC's tolerance is
carry-drift aware for the same reason). Supersedes nothing. Prevent-half
(exit-lifecycle hardening) is deferred to a separate cycle by ruling R3/R4.

## Context

### Motivating incident (Aug 14)

A live VPS reattach after the V2.5 deploy halted 3 of 6 sides and required a
4-pass manual reconciliation. Two failure modes were invisible to all tooling:
an ORPHAN exit order (a resting exit whose position was gone, left by a manual
close the EA never observed) and a ONE-LEGGED side (a missed reattach). Pipshed
showed no warning because its telemetry payload sends "working_orders":{}
(empty) and its alert banner only relays EA-emitted system_alerts -- it has no
independent book logic. So the check must live in the EA.

### HALT_21 is correct; orphans are upstream (source-verified)

The reattach halts were not an SRE bug. The reconstruction matcher requires a
perfect, volume-aware, consume-everything assignment (V2_SRE_AssignRecurse
terminal check: every exit must be used); an exit no position can justify
breaks the search -> HALT_21. It correctly fail-closes on an inconsistent
book. The orphan is created UPSTREAM: normal layer removal always cancels the
exit (Long_RemoveLayerAt -> V2_CancelExitOrder), but the async CloseBy window
(memory-only queue) and external/manual closes can strand an exit. BCC detects
the same condition HALT_21 catches, but while the side is LIVE -- hours before
a reattach turns it into a halt.

### The blind spot BCC fills

The existing per-tick Long_/Short_AuditExitLimits() is LAYER-FIRST
(position -> exit): it only inspects exits referenced by a layer, so it cannot
see an orphan whose layer is gone. BCC adds the complementary EXIT-FIRST
direction (exit -> position): does a live position justify this exit?

## Decision

Add a passive, detect-only Book-Consistency Check in the EA
(ea/fxmatrix_v2_bcc.mqh). It reconciles the live book against broker truth and
emits system_alerts on PERSISTENT inconsistency. It never cancels, closes, or
issues any trade op.

Four checks:
- C1 ORPHAN EXIT: enumerate managed exit-magic items (9x3/9x4) from BOTH
  OrdersTotal AND PositionsTotal (a crash-stranded hedge is a POSITION,
  invisible to an order-only scan). Primary pairing by ticket
  (layer.exit_ticket); for an unbound exit, fall back to the SRE's own
  assignment. Ambiguity -> UNVERIFIABLE (an alert), never "justified".
- C2 NAKED POSITION: an entry-magic position with no live resting exit
  (persistent).
- C3 ONE-LEGGED / DEAD SIDE: a side that should quote/hold but does not;
  cross-checked against halt state so a by-design HALT (ADR-113 HALT_09)
  reports HALTED, not a spurious BCC alert.
- C4 DUPLICATE PENDING: excess entry orders on a side.

Rulings (Gemini, Phase 2 + follow-ups):
- R1: C1 primary = ticket-binding; fallback = the SRE's global volume-aware
  assignment; ambiguity = UNVERIFIABLE. MANDATED -- reuse, do not reimplement.
- R2: C1 scans PositionsTotal AND OrdersTotal. MANDATED.
- R3: detect-only for v1. No queue journaling, no deferred layer removal
  (live-path risk outweighs the unmeasured crash-strand threat).
- R4: split cycles -- BCC (detect) now; exit-lifecycle hardening (prevent) as
  a separate, scrutinized follow-up gated on live occurrence data.

Scheduling (three-tier, to keep the combinatorial cost off the hot path):
Tier 1 ticket-binding check every tick (O(n), piggybacks AuditExitLimits);
Tier 2 SRE-assignment fallback EVENT-GATED (only on an unbound exit); Tier 3
full C1-C4 sweep throttled by InpBccSweepSec (default 60s) with a
2-observation debounce; one OnInit pass after reconstruction commits (no-op on
a halted side).

## Rationale

### Reuse, not reimplement (the R1 guarantee)

BCC builds V2SREPositionInput[] / V2SREExitOrderInput[] from the live pools and
calls the SRE's own functions: V2_SRE_Tier1Eligible / V2_SRE_Tier2Eligible /
V2_SRE_ExpectedExitPrice, and V2_SRE_MatchExitOrders
(state_reconstruction.mqh:585) -> V2_SRE_AssignRecurse (line 497), the same
consume-everything assignment that raises HALT_21. So a book BCC calls clean
provably reconstructs clean -- BCC and the reconstruction agree by construction,
not by approximation. Proven by unit test Test_BCC_ParityUnambiguousOrphan
(BCC flags exactly the unmatchable exit through the real match path).

### Teardown outcome (DeepSeek Phase 1, source-verified)

Commissioned AFTER a source pass, so grounded: 4/4 findings valid, 0
over-flags. Headline (T-2/T-3): an existential per-exit "is there a justifying
position" is weaker than the SRE's global volume-aware assignment -- a naive C1
could greenlight a book that HALT_21s. Fixed by mandating the SRE-assignment
fallback and dual-pool scan. T-5: the CloseBy queue is memory-only, so a crash
strands an exit-side position an order-only scan cannot see -> dual-pool
required. T-1: the CloseBy suppression gate must key on counterparty LIVENESS,
not queue membership.

### UNVERIFIABLE is a rare backstop, not a common outcome (finding)

Building the tests revealed that V2_SRE_Tier2Eligible has an exclusivity guard
(a position is Tier2-eligible for an exit only if that exit matches no other
position's Tier1 formula) and the Tier2 rollover band is directional/one-sided.
The SRE thus actively resists the "one exit, two eligible positions" state that
triggers UNVERIFIABLE (tier2_matches > 1). Consequence: BCC is more DECISIVE
than the design language implied -- it almost always reaches ORPHAN or JUSTIFIED,
and UNVERIFIABLE fires only in a narrow geometric corner. This is an
architectural strength (ratified by Gemini). It is why UNVERIFIABLE is covered
by a direct predicate test (Test_BCC_UnverifiableAmbiguousTier2Band) rather
than through the full integration path, where a passing fixture would be
brittle against tolerance changes.

## Verification

- Unit tests: BCC suite green; the only reds are the 8 authorized ADR-108
  C3/C5 HALT_30 baseline. Key coverage: ticket-binding (live vs gone),
  SRE-parity orphan (R1), dual-pool stranded position, CloseBy liveness gate,
  debounce, one-legged, duplicate, UNVERIFIABLE predicate.
- GUI compile 0/0 across the three unified shells and the tests EA.
- Detect-only confirmed: bcc.mqh contains no OrderDelete / PositionClose /
  OrderSend / CloseBy; CloseBy references are read-only liveness checks.

## Consequences

Positive:
- The Aug-14 orphan and one-legged side would both have been flagged LIVE,
  hours before a reattach turned them into halts.
- Reuses the SRE matcher, so BCC and reconstruction cannot silently diverge.
- Surfaces via the existing pipshed banner with zero pipshed change.

Non-goals / deferred:
- No auto-remediation; reconciliation stays a human action (live-account
  safety).
- No live-path change: CloseBy queue journaling and deferred-layer-removal are
  the separate prevent-half cycle (R4), gated on live crash-strand frequency.
- Pipshed "working_orders" population (for a cross-instance panel) is a
  fast-follow.
