# ADR-083 — Delete Invalid PRE-FILL Swap-Drift Loop (RunDailyRolloverReconciliation)

**Status:** Accepted

## Problem: ADR-045 Section 1 Applied Swap-Drift to Unfilled Pending Orders

`RunDailyRolloverReconciliation()` (ADR-045) contained two sections:

1. **PRE-FILL (deleted):** iterated `OrdersTotal()` / `OrderGetTicket()`, filtered by `EA_MAGIC` and `EA_MAGIC + 1`, and applied `TRADE_ACTION_MODIFY` price drift to matching `BUY_LIMIT` / `SELL_LIMIT` orders based on `ORDER_TYPE`.
2. **POST-FILL (retained):** iterated `g_inventory_0/1/2`, gated on `position_ticket != 0`, and adjusted tickets from `exit_tickets[]` using layer `direction`.

Section 1 was intended to translate daily swap costs into spatial price drift on parked entry limits. In practice it modified **every** pending limit order on the symbol with matching magic — including exit limits whose `ORDER_TYPE` matched the drift branch — with no struct-field linkage to distinguish entry from exit.

## MT5 Pending-Order Invariant

`OrdersTotal()` / `OrderGetTicket()` in MT5 returns **pending orders only**. An order leaves this collection the instant it fills and becomes a position. Every ticket Section 1 could ever process therefore has **zero accrued swap** by definition, regardless of magic number. Applying swap-drift adjustment to such tickets is invalid: there is no swap cost to reconcile on an unfilled order.

## Double-Modification Risk

Section 1 classified tickets by `ORDER_TYPE` alone. For a BUY layer, the exit is a `SELL_LIMIT`; for a SELL layer, the entry is a `SELL_LIMIT` and the exit is a `BUY_LIMIT`. Section 1 could therefore modify exit limits found in the pending-order pool **before** Section 2 processed the same tickets via `exit_tickets[]` — creating double-modification risk against Section 2's already-correct, inventory-driven exit handling.

## Decision: Delete Section 1 Wholesale

Remove the entire PRE-FILL block (comment + `OrdersTotal()` loop). Do **not** add magic-number filtering or struct-based entry/exit discrimination to salvage Section 1 — the underlying premise (swap-drift on pending orders) is wrong regardless of filtering.

**Retained unchanged:** Section 2 exclusively handles the only valid case — exit limits on genuinely open positions (`pos_tkt != 0`), using layer-direction-based swap selection and drift math. Section 2 does not read anything Section 1 produced; it is fully independent.

**Also unchanged:**

- Broker window gate (`dt.hour == 0`, `g_last_rollover_day_of_year`)
- Swap-mode check and `swap_long` / `swap_short` retrieval (Section 2 consumes these)
- `SaveAllInventoryState()` and closing diagnostics
- `IsClearOfFreezeLevel()` definition

## Test Coverage
