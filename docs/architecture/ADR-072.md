# ADR-072 — Conditional CloseBy Queue Exhaustion Handling

**Status:** Committed (pending)

## Context

When an exit limit fills on a hedging account, `HandleExitFill()` queues a `CloseByTask` pairing the original entry position (`ticket1`) with the new hedge leg (`ticket2`). `ProcessCloseByQueue()` retries `TRADE_ACTION_CLOSE_BY` up to 10 times per `OnTick` visit.

The original exhaustion branch (pre-ADR-072) assumed the two legs were always **delta-neutral** — opposite directions offsetting each other — and silently discarded the queue task with a WARNING only. That assumption was **correct for the normal unwind path** where `PlaceExitLimit()` places an exit on the side opposite to `Layer.direction`, and both legs genuinely offset.

ADR-071 traced the **corruption case**: if internal direction belief is wrong, the exit hedge can open the **same** broker direction as the entry. CloseBy then fails persistently (invalid same-direction pairing). Meanwhile `HandleExitFill()` may already have removed the layer from inventory based on exit-volume accounting alone. The exhaustion path then discarded the task with no alert and no halt — leaving **live, unmanaged, same-direction exposure** invisible to the EA until a future `OnInit` orphan check.

This ADR closes that gap with **conditional verification** at exhaustion time, not a blanket halt on every persistent CloseBy failure.

## Decision

**Three files changed:**

| File | Change |
|------|--------|
| `LayerStruct.mqh` | Add `int last_retcode` to `CloseByTask` |
| `ExecutionEngine.mqh` | Initialize `last_retcode = 0` at enqueue |
| `FXMatrix.mq5` | Capture `last_retcode` on OrderSend failure; replace exhaustion branch |

### `last_retcode` field

Stores the most recent failed `OrderSend` retcode for the task. Initialized to `0` at enqueue. Updated as the **first line** of the existing failure branch (Print unchanged). Included in exhaustion log/alert strings for diagnostics.

### Conditional exhaustion logic (after 10 retries)

On exhaustion, before removing the task from the queue:

1. **Select both tickets** — `PositionSelectByTicket` for each; read `POSITION_TYPE` immediately after each successful select.
2. **Both selectable (`sel1 && sel2`):**
   - **`type1 != type2`** — Genuinely opposite legs. **Original behavior preserved:** WARNING log, discard task, **no halt**. Message updated to state opposite direction was **verified**, not assumed.
   - **`type1 == type2`** — Same-direction legs. **ADR-071 corruption scenario:** push critical alert to `g_critical_alerts[]`, set `g_halted = true`, **no `ExpertRemove()`** (soft-halt only). Task still removed from queue.
3. **One or both unselectable (`!sel1 || !sel2`):** INFO log, **no halt**, task removed. **Judgment call at implementation time** (not an explicit prior Staff ruling): follows ADR-071 precedent that closed/stale tickets are a clean skip, not a mismatch. If one leg remains open untracked, `CheckForOrphans()` at next `OnInit` covers it — same category as any other orphan. **Flagged for revisit** if live behavior proves this too permissive.

**In all three branches:** `ArrayRemove(g_closeby_queue, i, 1)` runs once at the end — task always leaves the queue.

### Severity: soft-halt only

Same-direction exhaustion sets `g_halted = true` but **does not** call `ExpertRemove()`. Rationale: by exhaustion time the layer is often already removed from inventory; the EA's directional map is not corrupted in the ADR-071 sense — it has **unmanaged broker legs** it can no longer CloseBy. Same category as `CheckForOrphans()` soft-halt, not ADR-071 hard-kill.

Detection/alert only — no change to retry count, OrderSend success path, or symbol-mismatch branch.

## Negative space

- Retry mechanics (10 attempts) — unchanged
- CloseBy `OrderSend` success path — unchanged
- Symbol-mismatch branch (`g_halted`, separate case) — unchanged
- Non-exhaustion retry / history-select block — unchanged
- `CheckDirectionConsistency()` (ADR-071) — untouched
- No `ExpertRemove()` anywhere in this change

## Consequences

- Normal opposite-direction CloseBy failures still discard silently (verified, not assumed)
- Same-direction exhaustion after persistent failure now produces telemetry-visible critical alert and soft-halt
- `last_retcode` available in exhaustion messages for broker-side diagnosis
- Unselectable-at-exhaustion case remains no-halt by explicit implementation judgment — may be revisited
