T-1 D9 adoption paths — BREAKS.
Evidence: In `Grind_BreakerOnTick`, if `g_grind_breaker_allowance <= 0.0`, it emits `BREAKER_NO_BASIS` and returns (grind_engine.mqh ~940-952, INFERRED; ADR-159 F5 cites :906-935, :940-952). That return occurs before `Grind_BreakerAdoptPeerTrip`, before the own-trip block, and before the cancel-once block. Therefore an instance with no basis will NOT adopt a peer GV trip, will NOT set `g_grind_breaker_tripped`, will NOT block entries via `Grind_EntriesBlocked` (which reads `g_grind_breaker_tripped`), and will NOT cancel its ENT orders. Also, if `InpBreakerEnable=false`, `g_grind_breaker_enabled=false` and the function returns at the top (`if(!enabled) return;`), so no adoption occurs; `Grind_BreakerBlocksEntries` requires `g_grind_breaker_enabled`, so entries are not blocked even if the peer GV is set (grind_engine.mqh `Grind_BreakerBlocksEntries`, INFERRED). On the same tick, when adoption does occur, it sets `g_grind_breaker_tripped` before `Grind_OnTickEngine`, so `Grind_EntriesBlocked` is true and entries are blocked same-tick. Cancel runs exactly once because `g_grind_breaker_cancel_done` is set after the attempt (no retry on failure). Halted/quarantined instances: `Grind_BreakerOnTick` is still called before the halted/quarantined returns, so adoption and cancel still execute; entries are already blocked by halt/quarantine. Restart mid-day with GV set: the key-change branch sets `g_grind_breaker_tripped = GlobalVariableCheck(...)` after the allowance check, so adoption, blocking, and cancel-once occur — unless the no-basis early return fires.
Smallest fix: move the peer GV check/adoption before the allowance early-return, and make `Grind_BreakerBlocksEntries` return `g_grind_breaker_tripped || (g_grind_breaker_enabled && g_grind_breaker_premidnight)` so an adopted trip blocks entries regardless of `InpBreakerEnable`. For no-basis, still adopt and cancel if the GV is set.

T-2 Cancel path under D9 — HOLDS.
`Grind_CancelOwnEntryOrders` only cancels orders whose parsed comment role is `"ENT"` and slot matches (`if(c_role != "ENT" || c_slot != slot) continue;`, grind_engine.mqh `Grind_CancelOwnEntryOrders`, INFERRED). It ignores `"EXT"` exit orders and does not touch `exit_order_ticket` or `exit_position_ticket`. It updates `l0_pending_ticket` / `add_pending_ticket` on cancel or disappearance. Purgatory-held entries (`add_held`) are not cleared, but D9 blocks new entries, so they cannot be placed. Running on an instance whose own equity never tripped is the intended D9 behavior. No interaction with the exit queue reprice path. No fix.

T-3 Blocking flush at the roll — NEEDS-FIX.
`Grind_SnapshotEmit` ends with `Grind_ArchiveFlush(true)` (grind_snapshot.mqh `Grind_SnapshotEmit`, INFERRED). `Grind_ArchiveFlush` calls `Grind_TelemetryWebPostStatus` (grind_archive_flush.mqh, INFERRED), which is a synchronous MQL5 `WebRequest`. Default timeout is 5000 ms. At 22:00Z this blocks `OnTimer`, and MQL5 serializes events, so ticks/fills are delayed up to the timeout plus network. The candidate `Grind_ArchiveFlush(false)` is insufficient: the throttle only skips if `now_ms - last_flush_ms < 2000` (grind_archive_flush.mqh), and `OnTimer` already calls `Grind_ArchiveFlush(false)` immediately after `Grind_SnapshotOnTimer()`, so the snapshot is still flushed in the same `OnTimer` call. Smallest effective fix: remove `Grind_ArchiveFlush(true)` from `Grind_SnapshotEmit`, and move the existing `Grind_ArchiveFlush(false)` in `OnTimer` to before `Grind_SnapshotOnTimer()`. That defers the snapshot flush to the next timer tick (up to 1 s later), allowing ticks to process before the synchronous block.

T-4 Account switch — NEEDS-FIX.
`Grind_SnapshotEmit` tests `start_known` only as `GlobalVariableCheck(GRIND_SNAPSHOT_START_DAY) && (int)GlobalVariableGet(GRIND_SNAPSHOT_START_DAY) == ended_num` (grind_snapshot.mqh `Grind_SnapshotEmit`, INFERRED). It never checks account login. If a new account is attached with stale `GRIND_SNAPSHOT_START_*` from the old account, the first row can use the old account’s balance/equity with `start_known=true`. Smallest fix: add `GRIND_SNAPSHOT_START_LOGIN`; write it when writing the new day’s start values; in the `start_known` test require `(long)GlobalVariableGet(GRIND_SNAPSHOT_START_LOGIN) == AccountInfoInteger(ACCOUNT_LOGIN)`. Add the prefix to the D8 clean-up script.

T-5 Degraded terminal at the roll — NEEDS-FIX.
`Grind_SnapshotEmit` does `if(HistorySelect(win_from, win_to)) { ... }` but if `HistorySelect` fails, `deal_swap_day` and `nontrade` remain 0 with no flag (grind_snapshot.mqh `Grind_SnapshotEmit`, INFERRED). `TimeTradeServer() - TimeGMT()` may be stale if disconnected. The row currently reports zeros as if known. Smallest honest flag: capture `const bool history_ok = HistorySelect(...)` and add `"history_ok": true/false` to `Grind_SnapshotJson`. Optionally emit `deal_swap_day` and `nontrade` as `null` when `history_ok` is false. One boolean is enough.

T-6 Archive pressure — NEEDS-FIX (minor).
D6 adds `EJECT_ACCEPTED`, `EJECT_REFUSED`, `EJECT_FILLED` to the same archive queue as `fill_log` (grind_archive.mqh `Grind_ArchiveEnqueue`). The queue max is 5000, and when full it drops the oldest event (`Grind_ArchiveQueueRemoveFront(1); g_grind_archive_dropped++;`). Under a prolonged network outage, these extra events consume queue slots and can cause older `fill_log` rows to be dropped first. Eject events are bounded by auto-eject backoff (W minutes) and command frequency, so normal risk is low, but the crowd-out mechanism exists. Smallest fix: change the full-queue drop policy to drop the oldest `ea_event` whose code starts with `EJECT_` before dropping a `fill_log`, or reserve a minimum number of slots for `fill_log`. A simple high-water mark that rejects new `EJECT_*` enqueues when the queue is above, say, 4500 is smaller and protects fill logs.

T-7 Claim and GV lifecycle — HOLDS (with accepted gaps).
`Grind_SnapshotClaim` (grind_snapshot.mqh:68) uses `GlobalVariableSetOnCondition` for CAS. First-creation race: both instances may set 0.0, then only one CAS from 0 to day_num succeeds. A claimer that dies between claiming and emitting leaves the GV at day_num; that day’s row is lost, and no other instance retries. ADR-159 section 8 accepts a lost claimer as a gap. GV flush: `Grind_GvMarkDirty` is called after setting start values, `Grind_GvFlushIfDirty` runs in `OnTimer`, and `GlobalVariablesFlush` runs in `OnDeinit`. A crash before flush loses the start values; the next start falls back to history with `start_known=false`. Acceptable per D3. No fix.

T-8 C29 side effects — HOLDS.
`GRIND_CAP_ALL_MAGICS[18]` adds 22260701/22260702 with NZD legs (grind_cap.mqh). With cap thresholds 0.0, `Grind_CapThresholdEnabled()` returns false, and `Grind_CapAllowsEntry` returns true before any fleet iteration. `Grind_CapPublishOwnExposure` still writes GVs for the new magics, but no entry decision reads them when the cap is disabled. `Grind_MagicLockReleaseAllKnown` iterates the 18 magics for cleanup only. No behavior change on a live account with the cap disabled. If the cap is enabled, the new peers are correctly included, which is intended.

PREMISE VERDICT

Not safe to merge as-is. D9 has two real holes: the no-basis early return skips adoption entirely, and an instance with `InpBreakerEnable=false` never adopts or blocks. Both allow an instance to keep entering after a peer tripped the account breaker. T-4 can silently label stale start values from a different account as known. T-3 adds a forced synchronous `WebRequest` at the roll, blocking ticks up to the timeout. T-5 reports zeros when history is unavailable without saying so. The remaining threats either hold or are acceptable per ADR-159. The smallest fixes are local: reorder/guard D9 adoption, add `GRIND_SNAPSHOT_START_LOGIN`, remove the forced flush and reorder the timer flush, and add a `history_ok` flag. After those, the implementation matches ADR-159’s intent.
