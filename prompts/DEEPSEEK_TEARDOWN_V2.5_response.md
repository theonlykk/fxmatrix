## T-A' — Mid-flight crash / POSITION_PRICE_OPEN fallback

**VERDICT: EXPLOIT-FOUND** (localization failure in the fallback; not a request to build crash-atomic persistence).

**LOAD-BEARING CLAIM**
The fallback assumes the crash recovery is localized to "that one position." But D1 defines the origin as **per-side, shared**: there is one `L0'` for `MM_LONG` and one for `MM_SHORT`. Therefore `POSITION_PRICE_OPEN` is not merely rebuilding one position's exit; it is writing a *side-level origin* that the reconstructor will use to derive the side's ladder and other positions' exits. Check the D4 fallback path and `SreRebuildSide()`: does the recovered origin enter the same shared `L0'` variable that future qualifying exits will overwrite? If yes, localization is false.

**MINIMAL REPRO / MECHANISM**
1. Side has anchored origin `L0 = 10`, open positions at `18` and `30`, exit-hedges at `21` and `33`.
2. The `18` position's exit fills at `21`. Code sets `L0' = 21` and starts deleting/rebuilding the ladder.
3. VPS hard-crashes before the new ladder is posted and before the new origin is durable. Closed-deal history is forbidden, so `21` is unrecoverable.
4. On restart, the fallback takes `POSITION_PRICE_OPEN` of the surviving position `30` as the reconstructed origin.
5. SRE now derives the side ladder from `30` instead of `21`. Correct rebase ladder would start at `29`; fallback ladder starts at `38`. If the SRE re-posts exits for other side positions off the `30` origin, a later exit fill — one that would not have been a legitimate ratchet point under the true `L0'=21` — can still look like a clean harvest and re-base the origin again.

So the crash does not just lose one origin value; it can inject a false origin into the **shared side state** and have that false origin propagate through subsequent clean harvests.

**SEVERITY: fixable-within-design**
Fixable by treating any recovered origin as `L0_UNKNOWN`: do not use it to re-derive other positions' exits; allow the next genuine clean harvest to write a new origin from its own fill price. This is not fatal to the premise.

## T-1 — Re-base chain drift (within-side)

**VERDICT: EXPLOOT-FOUND**

**LOAD-BEARING CLAIM**
The re-base rule is `L0' = exit_fill_price`, and a qualifying exit price is approximately `entry_layer_price + add_to_exit` (or `entry_layer_price - add_to_exit` for the opposite direction). If the ladder entry is at `L0 + s_k` with `s_k > add_to_exit`, then:

`L0' = L0 + s_k ± add_to_exit`

This is not a contraction. It is a step in the direction of the favorable leg. The "min layer spacing > add-to-exit" invariant only guarantees the *first* rebased layer lands inside the old corridor. It does **not** prevent the next rebase from stepping the whole corridor again.

Check the formula in the rebase function: if `s_k - add_to_exit > 0`, then a qualifying exit always moves `L0'` by a positive amount for that side. The only way to get bounded oscillation is if exits alternate between upward and downward entry layers; nothing in the mechanism forces that.

**MINIMAL REPRO / MECHANISM**
Static range example, long-side ladder, origin `L`, first entry at `L+8`, exit target `+3`:

- `L0 = 10`. Price falls to `18` (buy), rises to `21` (qualifying exit) → `L0' = 21`.
- New ladder from `21`: first entry at `29`. Price later rallies to `41` and retraces to `29` (buy), then bounces to `32` (exit) → `L0'' = 32`.
- New ladder from `32`: first entry at `40`. Repeat → `L0''' = 43`, etc.

Fill sequence: `18 → 21 → 41 → 29 → 32 → 52 → 40 → 43 → ...`

Within any finite static range, `L0'` walks monotonically to the upper edge of the range and then the side goes dormant. It does **not** converge to an interior fixed point, and it does **not** oscillate stably around the range. In a slowly trending market it can walk without bound until the geometry depth limit.

This directly attacks the claim: *"re-base tracks the band, does not march out."* It marches to the boundary of the band.

**SEVERITY: fixable-within-design, but primary**
This is the core failure mode the D5 test must be powered to detect. It is not fatal to the underlying market-making premise, but it can make the re-base arm stop harvesting in the exact regime the test selects. If the D5 test passes anyway, the test is likely under-powered.

## T-2 — Rollover ghost/spike and carry-shift invariant

**VERDICT: EXPLOIT-FOUND** on the residual hole; the invariant is **not** proven safe without an additional carry constraint.

**LOAD-BEARING CLAIM**
D2's clean-harvest-only filter is a magic-number check. A qualifying exit is just an order with the correct harvest magic that fills at approximately `entry + 3`. D3's spread-check checks spread at the instant of fill. Neither check looks at *whether the fill was generated by a rollover quote artifact* or whether the next tick confirmed the fill.

The carry invariant is:

`effective_exit_distance = add_to_exit + carry_shift`

The safe condition is:

`effective_exit_distance < min_layer_spacing`

for **every** layer pair and **every** pair. The brief only asserts the base case: `spacing ~8 > add_to_exit ~3`. If `carry_shift >= spacing - add_to_exit`, then a carry-adjusted exit can land **on or beyond the next ladder layer**, and the "lands inside the old corridor" guarantee breaks.

**MINIMAL REPRO / MECHANISM**

*Ghost/spike via rollover:*  
1. At `16:59:59`, a long entry at `P-3` has a resting exit-hedge sell limit at `P`.
2. At `17:00:00`, the broker's rollover/swap adjustment prints a one-tick ask spike at `P`, while the bid-ask spread is normal (e.g., `0.8` pips).
3. The exit-hedge fills at `P`, correct magic, looks like a standard `+3` harvest, spread-check passes.
4. Re-base `L0' = P`; new ladder is posted at `P+8`, etc. At `17:00:01`, real liquidity returns at `P-6`, and the new ladder is off-market.

This is a residual hole. It is low-probability but mechanically possible. The fix is a rollover blackout window or a "two independent ticks after fill" confirmation, not merely a spread check.

*Carry-shift breaking the invariant:*  
Let min spacing be `8`, base add-to-exit be `3`. If carry/rollover adjustment shifts the effective exit target by `5` pips or more, the exit can land on or past the next layer. Concretely: entry at `18`, effective exit target `18 + 3 + 5 = 26` is still below `30`, but if the layer gap is the *minimal* `8`, then `entry + 3 + 5 = entry + 8` lands exactly on the next layer; `+6` lands beyond it. Once the exit is beyond the next layer, `L0'` is set to a price that overlaps or skips the old corridor, and the next ladder may be posted on top of a still-resting opposite-side/adjacent order.

This must be checked per pair with actual `AddPipsFloor` values, especially EURGBP and any pair-specific spacing. I cannot verify the numeric values from the brief; the formula is the load-bearing check.

**SEVERITY: fixable-within-design**
Fixable by capping the carry-adjusted exit target to strictly less than min spacing, or by treating any exit whose effective distance drifted from the base add-to-exit as non-harvest for re-base until carry-exact `L0'` is implemented.

## T-3 — MT5 Strategy Tester path-dependence

**VERDICT: TEST-INVALID**

**LOAD-BEARING CLAIM**
The pre-registered A/B test requires the tester to simulate a *dynamic, sequence-dependent* delete-and-replace of the whole ladder on a qualifying exit. MT5's Strategy Tester does **not** faithfully simulate the live race between:
- the exit fill tick,
- the deletion of the old ladder,
- the placement of fresh limits,
- and subsequent ticks trading through those fresh limit prices.

Check the `OnTradeTransaction` / `OrderSend` handling under Model=4 real ticks. Specifically, when a fresh limit is posted mid-tick, the tester can fill it against the high/low of the same tick or a synthetic next tick, while live would require the order to exist **before** a later tick trades at that price.

**MINIMAL REPRO / MECHANISM**
1. Real tick `T` touches the exit price; exit fills, triggering re-base.
2. Tester processes delete+place before the next tick. The next tick (or the same tick's range) trades through the new limit price.
3. Tester fills the fresh limit at the traded price. In live, that fresh limit was not resting in time for that tick, so no fill would occur.
4. The fixed-anchor arm never re-posts, so it never suffers this artifact. The two arms therefore diverge for an engine reason, not for a ratchet-mechanism reason.

Also, live broker-side queue priority / order-book position is lost when the dynamic arm deletes and re-posts; the tester usually has no queue model, so the dynamic arm is artificially favored.

**SEVERITY: fatal-to-verification, not fatal-to-premise**
The specified D5 test, as run in MT5 Strategy Tester, cannot be trusted. The mechanism may still be sound, but this test cannot prove non-inferiority. The verification path must change: forward shadow deployment, or a tick-level replay engine that models order placement gaps/queue/requotes.

## Section 6 — Red-teaming the D5 statistical design

**VERDICT: TEST-INVALID**

**LOAD-BEARING CLAIM**
The D5 protocol's window selection, delta construction, multiple-testing exposure, and fix-and-re-run rule are not pre-committed tightly enough to support a non-inferiority claim.

**MECHANISM / CRITIQUE**

1. **Window selection bias.**  
   "Choppy/range-bound windows" chosen before the run is not enough if the *specific* 20–30 windows are chosen by eye. The mechanism's failure mode is a slow one-way walk to the boundary; in a 6-hour choppy window that walk may look benign, while in a 24-hour range it may not.  
   **Fix:** pre-commit a mechanical window filter **before** seeing P&L — realized volatility band, Hurst exponent < threshold, no trend slope, range/ATR ratio — and then pre-list the exact calendar windows. Do not adjust the window list after seeing results.

2. **Delta = fixed-anchor arm's own cross-window dispersion is self-referential and gameable.**  
   If the fixed-anchor arm has one large outlier (e.g., a flash move), its cross-window dispersion explodes, the delta becomes huge, and the test becomes nearly un-failable. That is a degenerate case: re-base could be worse in every window and still pass.  
   **Fix:** cap the dispersion-based delta at the 10% floor, or pre-specify delta in currency/pips before any run. Do not let the anchor arm's noise define the acceptance band.

3. **Multiple-window / multiple-guard false-pass exposure.**  
   With 20–30 windows and two guard metrics, "pass" needs a single pre-registered aggregation rule. If the rule is "re-base must be non-inferior on the aggregate window P&L and pass both guards," one can apply a simple Holm/Bonferroni correction to the guards. If the rule allows vetoing on any single bad window post-hoc, the effective false-pass rate is uncontrolled.  
   **Fix:** pre-register one primary paired statistic (e.g., paired one-sided test on per-window net P&L) and state the exact guard thresholds before running.

4. **"Report full distribution, fix-and-re-run on concentrated loss" is a back-door to overfitting.**  
   This is legitimate **only** if the fix is pre-specified as a direct response to a pre-registered threat (e.g., "if loss concentrates in rollover windows, add rollover blackout") and if the rerun uses a holdout set of windows not touched in the first run. Without that, fix-and-re-run is repeated in-sample re-tuning.  
   **Line:** one pre-registered fix and one holdout validation set. Any fix that is invented after seeing the distribution requires a fresh pre-registration and a fresh window set.

**SEVERITY: fixable-within-design, but the current D5 protocol is not a valid statistical object.**

## OVERRIDE CHECK

**No Override Rule invoked.**

No finding invalidates the *fundamental premise* of the layer-anchor ratchet. The mechanism failures identified in T-A', T-1, and T-2 are concrete but fixable within the design envelope. However, T-3 and Section 6 invalidate the *proposed verification path*: the MT5 Strategy Tester A/B as specified cannot support a non-inferiority claim, and the D5 statistical protocol as specified is gameable. The ratchet may still be sound, but it cannot be shipped on the current evidence path.
