## T-1 I6 and I3 around a roll

**Verdict: NEEDS-FIX (I3), I6 can quarantine on silent GV failure.**

I6: no direct path from the three listed mechanisms creates “VL exists + live exit at wrong price” in normal operation. A modify that succeeds at the broker but reports failure leaves no VL, so I6 fails on a wrong exit *without* VL. A `GlobalVariableSet` failure in `Grind_VLSet` or `Grind_CarryRecordShift` is silent and does leave VL missing or shift missing while the exit is moved:
`Grind_VLSet` does `GlobalVariableSet(Grind_VLName(position_ticket), level);` with no return check. If `GlobalVariableSet` fails after a successful modify, the exit is at the rolled price and there is no VL → I6 quarantine.

I3: **BREAKS** when `Grind_ExitQManageSide` cannot place the new required exit. After a roll, the queue runs and skips placement on slot guard:
`if(!Grind_SlotExitAllowed(limit, used)) continue;` before placing required ranks.
`Grind_LatticeRollLayer` calls `Grind_ExitQManageSide(...)` after setting the VL. If the new highest rank has no exit and the queue cannot place it, the next tick’s invariant check runs before `Grind_LatticeOnTick`:
`const bool ok = Grind_CheckBookInvariants();` in `OnTick` before `Grind_LatticeOnTick`. The naked required rank is visible to I3. Branch S can increase exit count by 2 (rolled rank0 + new highest), raising the chance of the slot guard.

Smallest fix: before committing the roll, ensure the queue can place the new required exit, or make the roll fail closed if `Grind_ExitQManageSide` could not place a required exit. At minimum, check `GlobalVariableSet` success in `Grind_VLSet` and halt if it fails.

## T-2 Gap loop

**Verdict: HOLDS (with GV-set caveat).**

The loop is bounded:
`for(int iter = 0; iter < max_layers; iter++) {`
Each pass re-checks depth, level, market, candidate:
`if(Grind_SideDepth(side) < max_layers) break;`
`const double level = Grind_Normalize(Grind_ComputeAddTarget(...));`
`const double mkt = is_long ? Grind_MarketAsk() : Grind_MarketBid();`
`if(!Grind_LatticeLevelCrossed(...)) break;`
`const int idx = Grind_LatticeCandidateIndex(...);`
`if(idx < 0) break;`

It can pick a candidate just PLACED by the queue (branch M) — LB7 does this after each roll. It can pick a candidate just CANCELLED by the queue (branch S) — LB18’s `7010` case. Neither causes a re-roll because `Grind_LatticeCandidateIndex` skips `Grind_VLHas(ticket)`:
`if(Grind_VLHas(ticket)) continue;`

Requests per level: branch M up to 1 modify + 1 remove + 1 place = 3. Branch S up to 0 modify + 1 remove + 1 place = 2 (or 2 places if the new highest lacked an exit, which would already violate I3). Per episode max 3 × `max_layers` per side. No re-roll unless `Grind_VLSet` silently fails, in which case the layer is not marked rolled and could be picked again.

## T-3 Candidate and ranks

**Verdict: NEEDS-FIX.**

The candidate is not always the highest rank. LB18 shows a middle-rank candidate when the book is non-monotonic (unrolled entries below rolled VLs). Branch S leaves queue/I3/I6 consistent only if the queue places the required exit; it does not if the slot guard blocks (see T-1).

Filled exit not yet processed: `Grind_LatticeRollLayer` sees `layer.exit_order_ticket != 0` and tries:
`if(!Grind_ModifyPendingPrice(layer.exit_order_ticket, price, magic)) { ... return GRIND_ROLL_MODIFY_FAILED; }`
`Grind_ModifyPendingPrice` fails because `Grind_SelectOurOrder(ticket, magic)` is false (the order is gone). The roll returns `GRIND_ROLL_MODIFY_FAILED`, archives `ROLL_REFUSED`, and `Grind_LatticeTrySide` sets a backoff. That is wrong: the layer is closing, not a real modify failure. The earlier guard `if(layer.exit_position_ticket != 0) return GRIND_ROLL_CLOSING;` never fires because `exit_position_ticket` is still 0 until the deal is processed.

Smallest fix: before attempting the modify, if `layer.exit_order_ticket != 0` but `!Grind_SelectOurOrder(layer.exit_order_ticket, magic)`, return `GRIND_ROLL_CLOSING` instead of `GRIND_ROLL_MODIFY_FAILED`.

## T-4 Carry pass mid-roll

**Verdict: BREAKS.**

`Grind_CarryExitPassBegin` captures `layer.exit_order_ticket`:
`Grind_CarryExitPassAppendWork(layer.position_ticket, layer.exit_order_ticket, ...)`.
`Grind_CarryExitShiftLayer` later uses that captured ticket. If a roll happens between steps and is branch S (no exit at capture), the work item has `exit_order_ticket == 0`:
`if(exit_order_ticket == 0) { if(Grind_CarryShouldCommitAccrual(false, false, true)) Grind_CarryAccruedSet(position_ticket, accrued_price); return true; }`
The roll then places a new exit via `Grind_ExitQManageSide`. The carry pass sets the accrued GV but does not modify the newly placed exit. The live exit remains at the old formula + old accrued, while I6 expects formula + new accrued → I6 quarantine. If the roll cancelled/replaced the exit, the captured ticket is stale; `Grind_ModifyPendingPrice` fails and the new exit is unshifted.

Smallest fix: at shift time, re-read the current `exit_order_ticket` for the `position_ticket` from the book instead of using the captured ticket.

## T-5 The level

**Verdict: NEEDS-FIX (risk).**

For an unrolled book, `Grind_ComputeAddTarget` anchors on the highest `layer_index`:
`const int depth_idx = Grind_FindDeepestLayerArrayIndex(side); if(depth_idx < 0) return 0.0; anchor = side.layers[depth_idx].entry_price;`
`Grind_FindDeepestLayerArrayIndex` uses `if(side.layers[i].layer_index > side.layers[best].layer_index) best = i;`.

If an add filled away from its lattice level (clamped/gap) and the book is non-monotonic, the highest `layer_index` may not be the true extreme entry. For long, if the deepest index is not the lowest entry, the first virtual level sits too high (shallower); for short, too low. The offset equals the difference between the actual anchor and the true extreme. `Grind_Normalize` rounds to symbol digits, up to 0.5 point error. `GRIND_PRICE_EPS` is `1e-9`, far below one point, so it does not mask a real breach but also does not correct rounding.

Smallest fix: for the no-VL anchor, use the true extreme entry (min for long, max for short) or validate monotonicity before using `layer_index`.

## T-8 Restart

**Verdict: HOLDS.**

`Grind_LatticeResetBackoff()` sets both backoffs and failure counts to 0. On reinit, `Grind_ReconstructState` rebuilds from broker tickets. VLs persist as GVs if flushed. `Grind_LatticeCandidateIndex` skips `Grind_VLHas(ticket)`, so a layer already rolled cannot be picked again. If a VL was lost to a crash, the first tick’s invariant check runs before `Grind_LatticeOnTick` and I6 fails closed. The first tick cannot re-roll a layer that still has its VL.

## T-9 Backoff

**Verdict: NEEDS-FIX.**

`now` is `TimeCurrent()` from the live tick. It can go backwards or stall; the backoff is stored as `g_grind_vl_backoff_long = now + (int)sec;`. If server time jumps forward, the backoff expires early; if it jumps backward, the side can be blocked far longer than intended. There is also a path that returns `MODIFY_FAILED` without a broker call: `Grind_LatticeRollLayer` when `layer.exit_order_ticket != 0` but `Grind_ModifyPendingPrice` fails because `Grind_SelectOurOrder` is false (closing layer). That sets a backoff for a layer that is actually filling, blocking the side for up to 60 s and wasting the daily API budget on no broker request.

Smallest fix: use a monotonic tick count for backoff, and distinguish not-selectable (closing) from a real modify failure before setting the backoff.

## PREMISE VERDICT

“Modify first, VL after, queue after” is consistent for both branches *as written*: branch M modifies and only then stores VL/offset/shift; branch S stores VL and lets the queue place. The consistency is not absolute because:
- `Grind_VLSet` and `Grind_CarryRecordShift` ignore `GlobalVariableSet` failure; a silent failure leaves VL missing or shift missing after the exit has moved → I6 quarantine.
- The queue-after step can fail to place a required exit on slot guard, leaving a naked required rank for the next tick’s I3.
- A stale `exit_order_ticket` on a filled-but-unprocessed exit produces `MODIFY_FAILED` and a backoff instead of `CLOSING`.

So the write order is correct, but the failure handling around it is not complete.
