## 1. WHAT WAS DEPLOYED, AND WHY IT CHANGED SHAPE

17g's checklist step 1 could not be executed as written. It said to set
`InpFillTimePlace = false` and `InpSlotNearReserve = 0` in the 14 non-GBPUSD
presets; neither input existed in ANY of the 18 `.set` files. MT5 applies the
compiled default for an input a preset omits, and the compiled default was
`true`. Compiling as things stood would have put all 16 instances on
fill-time placement at once.

Fix, approved by Gemini: flip the compiled defaults to `false` / `0` and let
`gbpusd_opt.set` / `gbpusd_alt.set` opt in at `true` / `8`. Identical live
behaviour, reversed failure mode. Step 1 shrank from 14 preset edits to 2.

**Gemini Q1 amendment, now in ADR-152 Rollout, verbatim:** the compiled EA
defaults for `InpFillTimePlace` and `InpSlotNearReserve` must be `false` and
`0`; pilot participation is strictly opt-in via preset files to enforce a
fail-closed posture against missing or stale configuration.

**Gemini Q2 amendment, now in the Phase 1 promotion gate, verbatim:**
`near_reserve_blocks` is a measurement, not a hard threshold, UNLESS telemetry
confirms `guard_total` breached the far-entry ceiling (186); if saturation is
reached the block counter must be non-zero to proceed to Phase 2.

ADR-152 T1 was also tightened: the no-`Sleep`/no-loop check must extract the
body of `Grind_SlotLockTryAcquire` and assert within that function only. A
file-level grep of `grind_exitq.mqh` MUST NOT be used -- it fails by design,
because `Grind_SlotLockAcquire` legitimately contains `Sleep(1)`.

## 2. THE FINDING THAT MATTERS MOST

**A compile-triggered reinit does NOT reload presets.** MT5 reuses the inputs
stored on the chart. The two ADR-152 inputs did not exist when these charts
were last attached, so all 16 took the compiled default.

This was observed directly: after the 04:59:34Z compile, GBPUSD OPT's Inputs
dialog read `false` / `0`. The pilot pair had to be reattached by hand with
Load -> `gbpusd_opt.set` / `gbpusd_alt.set` to pick up `true` / `8`. The API
key must be copied out and pasted back, because the preset file carries it
blank.

Had the default stayed `true`, the whole fleet would have switched at 04:59
and nothing in telemetry would have shown it (see s3). The fail-closed flip
was not theoretical tidiness; it was load-bearing within the hour.

Corollary: step 7 of the 17g checklist is a reattach of 14 charts, not a
preset edit plus compile.

## 4. MECHANICS WORTH KNOWING

- **Heartbeat splits by size.** Small books emit one `HEARTBEAT` line; large
  books split into `HEARTBEAT`, `HEARTBEAT_DETAIL` and `HEARTBEAT_BOOK`, and
  the ADR-152 tail fields ride on `HEARTBEAT_BOOK`. Grep for
  `GRIND_<pair>_<arm>\|HEARTBEAT_BOOK` to see them on GBPUSD.
- **`deploy.ps1` cannot copy presets, confirmed in the script.** The xcopy has
  no `/S` and the verify loop no `-Recurse`, and the destination is
  `MQL5\Experts\fxmatrix`, not `MQL5\Presets`. This is 17e s4 as source.
- **`fxgrind.mq5` is LF, not CRLF.** `.gitattributes` pins `*.mq5` / `*.mqh`
  to LF and `*.md` to CRLF. Reading `\r` out of a checked-out markdown file
  and generalising it to the source tree is wrong.
- **`git pull` may prompt on a failed pack unlink.** Answer `n`. It is
  housekeeping failing on a locked `.idx`, not the pull failing.
- **`copy /Y` is cmd syntax.** In PowerShell use `Copy-Item -Force`.

## 6. GEMINI ON THE TWO LOCKS (asked, answered, verified in source)

The no-retry / no-`Sleep` / no-stale-steal amendment was scoped to the
fill-time path only. The blocking `Grind_SlotLockAcquire` is deliberately kept
for tick-path entries, where sleeping is off the transaction thread and
therefore harmless; the spec said explicitly not to modify it. Reasoning is in
the memo at `31b8295` s4. Verified against source: `Grind_TryPlaceL0` and
`Grind_TryRecenterOppositeL0` are called only from `Grind_OnTickEngine`, and
`Grind_HandleSideDealFill` reaches the lock only through the try-variant.
`Grind_ExitQManageSide` never takes the lock. Two locks by design.

Residual, pre-existing and NOT a Phase 1 regression: the 10 s stale steal
lives in the blocking path, so a tick-thread holder stuck inside a long
synchronous `OrderSend` can have its lock taken while still inside the guarded
region. Unchanged from `c39fb84`. Pull the `send_logs` duration distribution
before deciding whether it matters.
