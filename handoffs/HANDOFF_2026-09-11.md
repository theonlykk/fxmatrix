## 3. ROOT CAUSES

### 3a. Phantom layers AND missing short scalp events -- FIXED, ACCEPTED (ADR-127)

One defect, two symptoms.

- `Grind_OnTradeTransactionEngine` offers every DEAL_ADD to the long handler,
  then the short handler.
- The OUT_BY branch of `Grind_HandleSideDealFill` called
  `Grind_MarkDealProcessed` BEFORE checking whether a layer on that side owned
  the deal. The processed set is shared by both sides.
- So the long pass consumed every short CloseBy deal: no `scalp_closed` event,
  and the short layer was never removed.
- Introduced in `1b9e255` (2026-09-07). V2 used per-side processed sets.

Fix `e486bb9`: mark processed only after a layer on this side matches. Tests
CB1-CB4 (614/628 before the fix as predicted, 628/628 after). Deployed 05:04Z.

Live confirmation after deploy: four SHORT scalps emitted with a real
`stack_depth` and no phantoms (EURGBP_OPT 09:00:57, EURGBP_ALT 09:15:24,
EURGBP_OPT 13:01:14, EURGBP_ALT 15:13:07 broker). Status Accepted in `d98804c`.

Defects (grind_engine.mqh / grind_recon.mqh at `ed5d9ff`):

1. **Stale state after a send.** Order sends block (item 12); fills arrive
   meanwhile and the tracker lags.
2. **`Grind_TryPlaceL0` treats "cannot select my order" as "order gone"** and
   places a new L0. It cannot tell filled from cancelled.
3. **The fill's transaction only clears the tracked pending if tickets match.**
4. **ENT-branch exit placement finds the layer by index** and
   `Grind_TryPlaceExitForLayer` overwrites the exit ticket unconditionally, so
   a duplicate index steals the first layer's exit.
5. **Reconstruction adopts a lone L0 pending without checking the side is
   empty.**

**ADR-129 (`4d8d4c0` tests, `444812a` fix, deployed 13:31:49Z):**
- P2: when a tracked L0 or add pending cannot be selected, check for a
  position with the same ticket (an MT5 position's ticket equals its opening
  order's ticket; confirmed on three live positions). If it exists, the order
  filled: keep the ticket and place nothing until the transaction arrives.
  Otherwise clear and proceed as before.
- P3: the ENT branch finds the new layer by position ticket, and
  `Grind_TryPlaceExitForLayer` refuses to overwrite an existing exit.
- P4: after placing the fill's exit, an L0 fill cancels any different tracked
  L0 pending; `Grind_ReconcileStrayL0` also runs each tick at the top of the
  engine and cancels an L0 pending on a side that holds layers.
- Remaining window: order gone and position not yet visible still re-quotes as
  before; P4 then cancels the stray. A stray that fills before the cancel gets
  its own exit and halts on I5 (non-quarantinable) with both positions covered.
- Accept after the first live `WARN GRIND_STRAY_L0` line with no duplicate
  following it.

### 3d. Missing exits (I3_*_NAKED) -- PROVEN; MITIGATED BY ADR-128

Proof, AUDCHF_ALT 2026-09-11 (UTC):

    10:35:40.980  CRITICAL invariant fail I3_LONG_NAKED, instance halts
    10:35:41.071  Journal logs the long L00 exit fill (deal #517766886)

The invariant fired 91 ms BEFORE the terminal logged the fill that covered it.
`Grind_CheckBookInvariants` rebuilds from broker positions then orders (not
atomic) on every tick; a fill in progress looks naked. A halted EA then ignores
all transactions, so the exit fill queued no CloseBy and a later short fill
got no exit. Four 09-10 I3 halts share the signature.

The invariant only checks the broker book's self-consistency; it never
compares against the EA's tracker. That is why phantom layers kept
`invariant_ok: true`.

**ADR-128 (`36398c6`, deployed 13:09Z):** I2_*_EXIT_DUP, I3_*_NAKED and
I4_*_ORPHAN_EXIT enter QUARANTINE instead of halting: engine frozen for the
whole instance, trade transactions and CloseBy still processed, exit retry
still runs. A passing check releases immediately. Halt only if the failure
persists >= 3000 ms (GetTickCount64) AND >= 3 consecutive checks. All other
invariants halt immediately. I3 proven live; I2 and I4 derived from source.
Status Proposed until a live quarantine release is seen.

Exit retry during quarantine is safe because it keys on the EA's own record,
not because it cures transients: in the proven case the layer still holds its
exit-order ticket, so retry does not fire. 3000 ms is a MINIMUM duration, not
a maximum.

**32. PROPOSED CYCLE 3: carry-aware quote skew (not scheduled).** Skew the L0
quotes when flat: tighten the side whose carry PAYS by x, widen the other by
x, keeping total width constant. This prices carry EXPECTED on inventory
about to be taken, which is distinct from ADR-135b (carry already INCURRED on
open layers); the two do not conflict. Rationale: fills per unit time scale
roughly as 1/distance^2 for a continuously re-quoted limit (4p vs 5p = 1.56x),
so a small skew changes which side fills first without changing total volume.

and about 0 on GBPUSD -- but the coefficient must be MEASURED, not assumed:
expected hold comes from scalp_history and fill_logs, which start producing
it now. Cost of tightening is not a smaller scalp (the exit is measured from
the entry) but worse entries relative to mid, hence deeper stacks -- also
measurable via stack depth distribution. MUST NOT ship mid-cycle: it changes
fill rates and would invalidate the cycle 2 A/B. Sequence: 135a, 135b, then
cycle 3 with its own A/B.

## 8. OPERATIONAL PLAYBOOKS AND TRAPS

**Before any recovery:** take a fresh status read; grep the VPS logs by PRICE
(log times are UTC) to capture the timeline. Halt state is evidence.

**I3 halt (naked position):**
1. Close the genuinely naked position by hand (the one with no exit and no
   tracker layer).
2. Remove and reattach the instance with its preset (not a parameter reinit,
   item 14).
3. Reconstruction derives CloseBy pairs for any layer whose exit already filled
   (`Grind_DeriveCloseByQueueFromBook`). Verified live on AUDCHF_ALT:
   `INFO GRIND_CLOSEBY success retry=1` at 12:14:08 UTC.
4. Status read. The book snapshot in `/status/` is sent every 60 s and can lag
   the EA by up to a minute.

**I5 duplicate-L0 halt:**
Before ADR-129 (as on AUDCHF_OPT, recovered 12:59Z): the later position had no
exit and a second exit sat at the first layer's price.
1. Close the uncovered duplicate position (the later ticket).
2. Delete the duplicate exit order -- the LATER one; keep the original.
3. Remove and reattach.
After ADR-129 each duplicate has its own exit at its own price:
1. Close the later duplicate position.
2. Delete the exit order placed at that position's fill time (price = its
   entry minus/plus exit distance); keep the first layer's exit.
3. Remove and reattach.

**Phantom layers** (should not recur after ADR-127): signature is layers with
`has_exit_position: true` while `book.positions` is empty. Procedure: status
read; Algo off; delete adds anchored on phantoms; reinit; status read; Algo on.

Traps:
- Deleting a stray add with Algo on while a phantom remains is futile:
  `Grind_EnsureAddNext` re-places it next tick.
- Pressing OK in EA properties without a change does NOT reinit; change a
  harmless input (e.g. `InpConfigWarning`) for `deinit reason=5`.
- Repo presets have a blank `TelemetryAPIKey`; if a dialog shows it blank the
  instance goes dark. Do not share screenshots of the properties dialog.
- A scalp recorded after a halt-and-recover carries the CloseBy time, not the
  exit fill time.
- Pipshed fetches: paste URLs on their own line or in a code block (the chat
  converts them into links whose target can differ); retry a failed fetch once
  before diagnosing.

**MQL5 facts learned the hard way:**
- A floating-point division by zero stops the EA with a critical error; it
  does not yield inf/nan. Guard every divisor.

  `HistoryOrderSelect`; the one-argument form does not exist.
- nan/inf appear from functions like `MathSqrt(-1)`; `DoubleToString` prints
  them as non-JSON text, so emit `null` when `!MathIsValidNumber`.
