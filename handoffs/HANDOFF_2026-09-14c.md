## 2. ADR-145 -- R1 DIAGNOSED AND FIXED (merged; test-only, no deploy)

**The diagnosis in `HANDOFF_2026-09-14b` s6 and in `01_BOOT.md` was wrong.**
Both say the failure means "the broker-comment lookup fell back to the
reconstructed form". No such fallback exists. `Grind_HeartbeatLayersJson`
initialises `comment_json` to the literal `"null"` and overwrites it only on a
successful lookup, emitting the stored string verbatim. `GrindCommentBuild`
has three production call sites, all order placement.

That wrong diagnosis was written by reading the assertion NAME, not the code.

**Real mechanism.** `Grind_TelemetryHeartbeatJson` returns `core + detail +
book`. Only `detail` honours `g_grind_heartbeat_test_active`. The `book` half
honours `g_grind_book_test_active`, a different flag, and when false it
enumerates the real `PositionsTotal()` / `OrdersTotal()`.
`Grind_TestResetLayerDetailState()` sets that flag FALSE, then R1 asserts a
string is absent from the whole heartbeat -- live book included.

**Confirmed against the live book, not inferred.** The status read at
`generated_at 2026-09-14T22:29:16Z` showed GBPUSD_OPT, magic 22260101, holding
ticket 541050954 with comment `GRIND|OPT|L|L01|ENT`, open since 06:18:17
broker. The desktop terminal that runs the suite is logged into the same
account (1514582088), so `PositionsTotal()` returns the VPS fleet's book.

**The apparent determinism was a stable live book, not a deterministic test.**
The GV isolation fix at `fc46d2f` was correlated with R1 settling on fail, not
causal. That causal claim was asserted without being tested.

**Scope was never just R1.** About twenty tests assert against the full
heartbeat string; only the seven `Test_B*` sites ever activated the book
harness. `Test_D5_NoTicketNumbersInJson` was the next collision waiting.

Fix is one line: activate the book harness empty in the shared reset. R1's
body is byte-identical to baseline -- it passes because the input was
isolated, not because an expectation was changed.

`grid_sim_v7_real_signal.py` is single-sided by construction -- the straddle is

## 4. SCALP TELEMETRY -- ONE DEFECT, NOT TWO, AND DO NOT "FIX" THE TIMESTAMP

A memo carried in from the previous chat reported a scalp date-key mismatch at
the broker roll: five instances reporting `scalps: 1` while `/scalps/` returned
zero records for 2026-09-15. It proposed that `close_time` carries broker time
mislabelled `Z` and that the EA and pipshed key "today" differently.

**Half right. The conclusion is wrong and acting on it would corrupt data.**

Confirmed: `Grind_IsoUtc` in `ea/grind_scalp_events.mqh` performs NO
conversion. It destructures the `datetime` it is handed and appends a literal
`Z`. The caller passes `DEAL_TIME`, which is broker server time. So the name
lies.

But the consumer expects exactly that. In pipshed `app.py`:

  - `_closed_record_date(record)` takes `close_time[:10]` and ignores the suffix
  - it compares against `_broker_today()`, which is
    `datetime.now(ZoneInfo(BROKER_TIMEZONE))` with `BROKER_TIMEZONE` defaulting
    to `Europe/Athens` -- which tracks the broker's DST rather than hardcoding
    GMT+3
  - every docstring says "broker calendar date" / "broker-today"

**Both sides are broker-dated and they agree.** Making `Grind_IsoUtc` emit true
UTC would shift `close_time[:10]` three hours earlier, and every scalp closing
between 21:00Z and broker midnight would land on the previous date while
`_broker_today()` returned the current one. That is the corruption the memo
feared, and it does not exist today. We would be introducing it.

`_closed_record_date` prefers a `trade_date` field when present. **fxgrind
never emits one** -- `trade_date` is a V2 field
(`TelemetryEngine.mqh`, `fxmatrix_v2_telemetry.mqh`, via
`V2TelBrokerTradeDate()`). pipshed never writes it either. The comment at
`app.py:116` describes V2 behaviour fxgrind no longer has. The fallback lands
on the same clock, so the outcome is correct.

**The single real defect: `g_grind_scalp_count` never resets.** Declared in
`grind_state.mqh:31`, incremented at `grind_engine.mqh:586`, and absent from
`Grind_ResetDailyPnlCounters` (which resets `realised_pnl_today`,
`scalp_pnl_last` and the penetration counters). It is lifetime-since-EA-init
sitting beside broker-daily fields. Confirmed empirically: all five non-zero
counters went to 0 at the recompile.

That fully explains the memo's observation. There was no ingestion problem and
no unfiled scalp.

**Not fixed, deliberately.** pipshed sums this field across cards at
`app.py:589` and renders it, so it is a cross-repo contract. Two options:
reset it daily (honest beside `realised_pnl_today`, changes what the fleet
reports) or add `scalps_today` (respects the append-only heartbeat schema that
`Test_D6_InstanceIdFirstSchemaAppendOnly` enforces). The second is safer. This
needs a Gemini ruling, and a deploy means twelve reinits, so it was not worth
spending the evening on.

## 5. OPERATIONAL FINDINGS

**A recompile on a consistent book is free.** All twelve reinitialised at the
ADR-143 deploy and `api_count` did not move -- still 18 fleet-wide. Nothing
needed placing because every book reconstructed clean. The expensive part of
the 09-14 recovery was the nine manual repairs, not the twelve reattachments.

**Proof the fleet reloaded, without trusting a report:** every `scalps`
counter went 1 -> 0 on five instances and ring `fills` went to 0. Since that
counter never resets by any other means, only a reinit can do it. Layer array
ordering also changed on GBPUSD_ALT (L01 before L00) -- reconstruction rebuilds
from broker enumeration order. `layer_index` intact; benign.

**`deploy.ps1` does not cover `ea\presets\`.** The copy is
`xcopy ea\* "$term\" /I /Y` with no `/S`, so subdirectories are skipped, and
the hash verification loop uses `Get-ChildItem -File` with no `-Recurse`.
Presets are therefore OUTSIDE the byte-identical guarantee. Harmless in
practice -- presets are loaded by path from the properties dialog -- but nobody
should assume "deploy.ps1 said OK" covers a preset.

**A third clock is now in play.** MetaEditor journal lines carry LOCAL machine
time (Toronto). A suite run stamped `2026.09.14 20:24:44` is `00:24:44Z` on the
15th. The `02_TRAPS.md` table should gain this row alongside `received_at`
(UTC) and `deal_time_broker` (GMT+3).

**The suite count is now a baseline, not just a gate.** 989/989. Note that
`Test_I5g_L2ReconstructionPasses` contains nothing but a call to
`Test_L2_ReconstructionCarriesCommentIndex`, which is separately registered, so
L2's 2 assertions run twice. A regression in `Grind_RebuildBookFromTickets`
would present as a TOTAL of 987 rather than as a FAIL line. **Report the total,
not just the failures.**
