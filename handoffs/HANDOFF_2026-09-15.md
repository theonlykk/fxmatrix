**Then we scored the live ring against the same window for the first time.**

All four live cells breach. The ring went live on calibration-only numbers and
had never been tail-gated -- `HANDOFF_2026-09-13` carried the open item

**Two mechanism theories proposed and REFUTED. Do not re-propose them.**
(a) Ladder span (Claude): wider add spacing gives less summed adverse excursion

including the `max_layers=8` conclusion built on it. (b) Turnover (previous
chat): narrow recycles while wide fills once and sits -- contradicted;
`mean_exits` does not collapse at width 7, every cell saturates the cap, and
`mean_l0_hold_min` is SHORTER at width 7. **No mechanism is currently known.**

## 2. OPTION 3 FAILED, AND WHY

Gemini ruled (ADR-146 D2) that NZDCHF be re-calibrated with a CHF-shock window
INSIDE the calibration set, so the optimiser balances chop harvest against tail
survival. `calib_tail_2015q1` was added as a calibration-role key mapped to the
existing slice.

**The re-calibration returned NO SELECTION.** `is_gate_disqualified` is binary
-- it eliminates rather than penalises. With the tail in the calibration set
every cell scores `-inf`, the average is `-inf` everywhere, Q3 selects `None`
and Q4 skips. The balancing mechanism Gemini described does not exist in the
scoring.

Exit 10 was added to the grid and did not rescue anything.

**Best cell in the 12-cell grid is 3/10**: highest realised (13,857) and lowest
drawdown (194.5) simultaneously -- and still 16% Gate A. Mean well inside the
limit, distribution not. The gate catches tail-of-the-tail behaviour that no
averaging fixes.

**Unresolved. Three routes, needs a ruling:** reject the pair; grade the
penalty instead of disqualifying (a scoring change affecting every future
selection); or sweep `max_layers`, which is the one lever never tried and the
one that acts directly on the failing mechanism -- every disqualified cell has
`cap_reached_rate` 100% and `mean_max_layers` 8.0. **`max_layers` is not a CLI
dimension of the sweep; it is fixed per pair in `sim_costs.py`.**

## 3. THE CAP WAS NEVER EXECUTABLE (ADR-149)

`Grind_CapPublishOwnExposure` writes GlobalVariables only for the two legs an
instance carries. `Grind_CapSumLegExposure("CHF", ...)` looped over all twelve
magics and read `GRIND2226_<magic>_CHF` for each. Eight of those keys have never
existed. `Grind_CapReadStoredPeer` treats a missing key exactly like a stale
one -- returns MAXED (1.0e12) and sets `failed_out`.

So arming any threshold would have blocked every entry on every instance from
the first tick, permanently. ADR-143 called this "latent". That was wrong and
ADR-149 corrects the record.

Fixed by leg isolation (Gemini R2): a static magic-to-legs table beside
`GRIND_CAP_ALL_MAGICS`, and a `continue` guard so a peer contributes to, and
can only fail, a leg it actually carries. A stale GBPUSD now blocks GBP and USD
fleet-wide but not CHF.

**Maintenance hazard, recorded:** leg membership lives in presets and the EA
cannot read a peer's preset, so the table is hardcoded. CL4 catches length
drift. **Nothing catches a wrong currency value.** It was verified once, by
parsing all twelve presets and cross-checking every row. Do that again whenever
the fleet changes.

Thresholds remain 0.0. Arming is a HARD BLOCKER for NZDCHF (ADR-146 D5) and for
any mixed-width barbell pair (Gemini R3).

## 4. THE JPY CARRY DEFECT -- AND A WRONG FIRST FIX

`_swap_pip_div` inferred the MT5-points-per-pip divisor from `PairSpec.point`.
But `point` in this codebase is PIP SIZE IN PRICE UNITS, not tick size -- stated
in a comment above the JPY specs and pinned by `test_t5_jpy_point_size`. The
inference was unsound at its root, and returned 1 instead of 10 for USDJPY and
AUDJPY. Their carry was overstated TENFOLD.

**The first attempt changed `point` to 0.001 on those two pairs. That was
wrong** -- it broke `test_t5_jpy_point_size` and `price_diff_to_usd`, which
depend on `point` being pip size. The branch was discarded. ADR-147 records the
rejected remedy so it is not re-derived.

Correct fix: `_swap_pip_div` returns 10 unconditionally. Every supported pair is
five-digit, three on JPY, so one pip is 10 points on all of them.

**How the wrong fix got approved:** the spec quoted the `PairSpec` blocks but
not the two comment lines directly above them. Gemini approved on the strength
of that audit. **Read the surrounding context, not only the lines you intend to
change.**

**Consequences:** AUDJPY's -56 ten-pair score is void -- it is untested, not
rejected. `fleet_carry_v2_2026_09_13` is affected.

**Note:** `origin/test/jpy-pip-parity` is a pre-existing branch titled "Add JPY
pip-value parity tests and ring pair specs." Nobody looked at it before this
work. It may contain prior analysis. Cut from a very old base (130 files,
24,722 deletions vs main) so not directly mergeable.

## 5. BARBELL ARMS APPROVED (ADR-148)

Operator proposal, Gemini approved. OPT carries the chop/ranging-optimal
geometry, ALT the stress-optimal, both deployed together, selected per regime
rather than pooled.

AUDNZD is the case: chop peaks 7/5 (268.29), stress peaks 3/5 (747.03), pooled
returns 3/5 -- the stress peak winning on magnitude, discarding the chop optimum
entirely. Both surfaces flagged PEAK with one cell within 5% of top; no plateau.

ADR-125 already warned "do NOT pool stress + ranging into one surface" and the
sweep printed that caveat on every run while pooling anyway.

**The exit A/B is retired (Gemini R2).** Arms now differ in width AND exit, so
the live gap measures regime-match, not geometry. Deliberate retirement of a
controlled experiment -- it is how the signal was retired and how cycle 2 chose
its exit arm.

`select_barbell_per_pair` groups by `WINDOW_META[w]["regime"]`, so `calib_tail_2015q1`
(regime `stress`) pools with `calib_stress_2022q1` automatically when present.

## 6. TOPOLOGY -- THE OPERATOR'S FINDING

The live fleet is **topologically uniform**: two closed triangles
(EUR/GBP/USD, AUD/CAD/CHF), six currencies, every currency in exactly two
pairs, four instances each. That is why a single cap threshold has never been
needed -- every leg carries identical worst-case exposure by construction.

**NZDCHF would have been the first chord**, taking CHF to 6 while NZD sits at 2.
That asymmetry is the only reason Gemini's 0.40 threshold needed a risk-appetite
call rather than falling out of structure.

The proposed pentagon -- CADCHF, CHFJPY, AUDJPY, AUDNZD, NZDCAD -- restores
uniformity: AUD, CAD, CHF, JPY, NZD at 4 each. Combined with the EUR/GBP/USD
triangle that is 8 currencies, 4 instances each, 16 instances, zero chords.

**Caveat: the pentagon contains CADCHF, which is in the current triangle.**
Running both takes AUD, CAD and CHF to 8 instances while the rest sit at 4 -- a
worse asymmetry than NZDCHF. The pentagon must REPLACE the AUD/CAD/CHF
triangle, which means retiring live, profitable AUDCAD and AUDCHF. That is a
fleet topology decision, not a pair addition, and it is unresolved.

## 7. PROCESS -- THREE SELF-CONTRADICTORY VERIFICATION CRITERIA

Today produced three Cursor prompts whose SELF-REVIEW section contradicted
their own DESIGN section:

  - ADR-143: design specified a blank line, a comment and a pattern (3 lines);
    verification demanded "2 insertions".
  - ADR-148: design specified a docstring mentioning `PairSpec.point`;
    verification demanded zero `PairSpec` grep matches.
  - ADR-149: ADR instruction required naming `InpCapLegAThresh`; verification
    demanded zero matches for it.

Cursor followed the design and ignored the impossible check every time. The
correction is on the spec author: **derive verification greps and counts FROM
the design text after writing it, never from memory.**

Related: the ADR-149 failure-mode list named `T27` and the C-series but missed
`CM2`, which the spec author had written that same morning for the same
function. Leg isolation superseded it (0.78 -> 0.42, see ADR-149). When
changing a function, grep for every test that names it.
