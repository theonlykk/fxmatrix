## 1. WHAT SHIPPED

### The stale-offset fix -- a LIVE latent halt, pre-existing

`GRIND_CARRY_SHIFT_<ticket>` records how far an exit was placed from its raw
formula, so I6 tolerates a legitimately off-formula exit. **Nothing ever
cleared it except a scalp close.**

Sequence, needing no carry at all: exit placed WITH a clamp (offset stored),
layer demoted below rank 0 (order cancelled, offset survives), layer promoted
back in a QUIET market (queue places at the raw formula, `price == formula`,
so the write guard `if(clamped || MathAbs(price - formula) > _Point * 0.5)`
is FALSE and the stale offset is neither updated nor cleared). I6 then
computes `raw + stale_offset` against a placed `raw` and halts the instance.

Measured: `CARRY-PROBE ... gv_after_replace=0.0002 ... I6 ok=false
reason=I6_LONG_EXIT`.

**Under K=1/H=0 an exit is cancelled on every add fill**, so the demotion
that triggers it is now constant. Fixed in four lines: clear on cancel (two
branches, NOT the filled-exit branch), and an `else` clearing on unclamped
placement. Five tests, `STALE-1` to `STALE-5`.

### F2 -- held layers never accrued carry

`grind_carry.mqh:767` and `:775` skipped any layer with
`exit_order_ticket == 0`, so a held layer accrued nothing and lost every
night it spent in purgatory when later promoted. On a five-layer ladder at
K=1/H=0 that is three fifths of the book, every night.

Fixed with a DEDICATED store, Gemini's Option B:

| store | holds | writer | cleared |
|---|---|---|---|
| `GRIND_CARRY_SHIFT_<t>` | actual minus intended | whoever places/modifies | cancel, unclamped placement, scalp close |
| `GRIND_CARRY_ACCRUED_<t>` | accrued carry, price terms | the carry pass ONLY | scalp close only |

    intended = raw + accrued
    SHIFT    = actual - intended
    I6       = raw + accrued + SHIFT == actual

**The previous attempt failed because it made the formula carry-aware with a
SINGLE store** -- the clamp block then stored the clamp delta alone and I6
lost the carry. Two stores closes it. Seven tests, `F2-1` to `F2-7`, and
`F2-3` is the first test ever of carry and clamp together.

The pass now iterates LAYERS: always record the accrual, modify the order
only if one exists.

### Also found, NOT fixed -- the placement path has the same normalisation bug

`grind_engine.mqh:1845-1851`. `Grind_PlaceLimit` normalises the price it
sends (`:423`), but both the stored `exit_target` AND the shift are computed
from the un-normalised value. Sub-point, well inside I6's `2 * point`
tolerance, so it halts nothing -- but `exit_target` records a price that was
never placed. **Pre-existing. Own branch. Not urgent.**

## 2. THE BARBELL (F1) -- BUILT AND MERGED, NOT DEPLOYED

Merged at `605bc85`. **Suite 1354/1354, operator-run.** The VPS still runs
`5454358`, so main is three production files ahead: `grind_engine.mqh`,
`grind_exitq.mqh`, `grind_recon.mqh`.

Design worked through by hand in
`docs/architecture/exitq-barbell-notes.md` (1,185 lines) and ratified by
Gemini before any code.

**The exit queue drops exactly the wrong layer.** Rank is ordered
nearest-to-market, so on a long ladder built downward the MOST UNDERWATER
layer carries the HIGHEST rank -- at `K=1` it is the FIRST exit dropped. That
is the ejection candidate, and under the prefix rule its order does not exist,
so an ejection must `OrderSend` into a saturated guard (the 73-minute
measurement, `roll-at-cap-notes.md` s3a).

**Rule:** `rest if rank < K OR rank == depth - 1`. Rank 0 plus the most
underwater; drop the middle. Costs at most ONE extra resting exit per side at
depth >= 2, and does not grow with depth -- every new layer arrives at rank 0
and pushes the previous rank 0 into the held middle. Only the two ends rest.

**As shipped**, both predicates take depth and are total:

    bool Grind_ExitQRequired(const int rank, const int depth)
    {
       if(rank < 0 || depth <= 0)
          return false;
       if(rank < Grind_ExitQK())
          return true;
       return (rank == depth - 1);
    }

`Grind_ExitQAllowed` is identical with `+ GRIND_EXITQ_H`. `K` stays 1, `H`
stays 0 -- **this changed the SHAPE of the queue, not its size.**

Call sites: `grind_engine.mqh:1814` and `:1819` pass `n`;
`grind_recon.mqh:493` and its short twin pass `long_count` / `short_count`.
**The queue and I6 must agree on which ranks require coverage** -- if I6
required a rank the queue holds, every instance would halt on
reconstruction.

## 3. PASSIVE EJECTION -- WEAKER THAN IT LOOKED

Five positives, eight negatives (`exitq-barbell-notes.md` s2h). The negatives
that emerged today:

- **The timing trade is bad at both ends.** Eject at cap and the trade is a
  wash -- buy 65, sell 65.002 -- having paid the full ladder width to swap
  the worst layer for one at market. Eject late in free fall and the refill
  bid clamps to a coin flip. Leave it unfilled while price runs and you have
  the ejection made, no benefit, still capped.
- **Revising lower as price falls is a trailing stop**, however passively it
  executes, and it destroys the self-timing property.
- **It is a patch for a geometry problem.** Eight layers at 10-pip spacing
  spans 80. GBPUSD's median daily RANGE is 95.
- **Both arms strand together.** Within each pair `width` and `add_pips` are
  IDENTICAL across OPT and ALT -- only `exit_pips` differs. **That is a
  harvest-rate difference, not a regime one.**

**Gemini ruling on staleness:** fire at cap; if unfilled, revise ONLY into a
stabilised market -- over the last N M5 bars, `high - low <= add_pips` AND
`low <= prospective_bid`. Bars via `CopyRates`, not a tick ring buffer
(survives restart). Repeatable, because a single revision freezes on a second
shelf. `N = 6` is his suggestion and a GUESS -- measure before speccing.

**Operator's framing, which reframes the whole question:** we do not make
money from MTM. An underwater layer that blocks scalping is not a position,
it is the absence of a strategy. And: did we confuse activity with
achievement? The 17-Sep manual closes were a P&L wash (-176.35 realised vs
-125.21 held); what they bought was a ladder INSIDE the trading range.

## 7. PASSIVE EJECTION -- WHAT IS LEFT

### Settled

- `OrderModify` of an existing resting order to `ask + min_dist` or higher.
  **The barbell (s2) is what guarantees that order exists.**
- No new state. I6 already compares the resting order against
  `exit_target`, so moving both together is consistent. Only a telemetry
  flag, so an unfilled ejection is visibly ARMED rather than looking like
  nothing happened.
- Fire at cap. **If unfilled, revise only into a STABILISED market** -- not
  on elapsed time, not on distance travelled, both of which act because the
  market moved against us.
- Repeatable, because a single revision freezes on a second shelf. Revising
  lower adds no loss: it converts unrealised to realised at the same price.
- **Ships behind a fail-closed preset input** -- `InpEnablePassiveEject`,
  compiled default `false`, presets opt in, with its
  `Grind_ConfigDumpString` entry in the SAME commit (G1 on 2026-09-18
  existed because ADR-152's inputs were added without one).
- A separate pre-ejection DELAY was proposed and rejected
  (`exitq-barbell-notes.md` s2j): the stability condition already provides
  that protection and measures the right thing, and a delay leaves the side
  frozen while price runs.

### Still needed

**1. Measure `N`.** The stability window is
`high - low <= add_pips` over N M5 bars, with the prospective refill bid
inside that range. **`N = 6` is Gemini's suggestion and he flagged it as a
guess.** If such a window almost never occurs the mechanism never fires.
Sweep N from 3 to 24 so we see the shape, not one number. Same M5 data as
the path study -- which ENDS 07-Sep to 11-Sep, so it will not cover the
operator week.

**2. Redo the sweeps, with ejection available as a variable.** The existing
`roll_modes_cal_2026_09_17` covered 2 of 5 pre-registered windows, is
single-sided, has no guard model, and `exits_per_forced_close` was
misdefined. **It informed nothing and must not be cited.**

Operator's point, and it changes the shape of the study: **geometry and
ejection interact.** A shallower ladder caps sooner and ejects more often but
cheaper; a wider one caps rarely and ejects expensively. Sweeping geometry
WITHOUT ejection describes a system we do not intend to run. One study
answers the geometry question and prices ejection together.

### Dropped

**`p` (the retrace probability) is no longer being measured.** It prices
recovery against HOLDING, but holding at cap is not the alternative --
**scalping is.** We do not make money from MTM. An underwater layer that
blocks scalping is not a position, it is the absence of a strategy. `p` was
the wrong denominator.

## 6. MECHANICS LEARNED

- **The VPS PULLS. Do not push from it.** A tag push revealed it holds write
  credentials. Create tags on the desktop. Recorded in `01_BOOT`.
- **Tag every VPS build before deploying over it:** `vps-<sha7>`, annotated
  with the UTC compile time. Restore is `git checkout vps-<sha7>`,
  `.\deploy.ps1`, compile.
- **A compile with the market shut is a valid test of RECONSTRUCTION** and
  nothing else. Good for defensive changes; useless for anything tick-driven.
- **`git pull` says "already up to date" after Cursor finishes** -- same
  machine. Check `git log --oneline -1` against the remote instead.
- **MetaEditor skips rebuilds when only an INCLUDE changed.** Delete the
  `.ex5` to force it.
- **MQL5 has no reference variables.** `GrindSideState &side = g_grind_long;`
  is a compile error; a value copy silently discards mutations.
- **`Print` truncates doubles.** Wrap diagnostics in `DoubleToString(v, 8)`
  or a sub-pip delta reads as `0.0` and inverts the conclusion.
- **`Grind_Normalize` moved to `grind_pure.mqh`** -- `grind_carry.mqh` is
  upstream of the engine and cannot include it back.
