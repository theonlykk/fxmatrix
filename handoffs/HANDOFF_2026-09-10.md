## 2. READ THE FLEET WITHOUT A SCREENSHOT

**This is the day's main achievement.** The full broker book is now readable
remotely.

    https://pipshed.com/api/g/k7m9p2x4q/status/<anything>

**The trailing segment is a cache-buster and must CHANGE each session.** The
assistant's fetch tool caches by PATH and strips query strings -- a `?v=2`
does nothing. Use `/status/20260911a`, then `b`, and so on. The server ignores
the segment entirely.

**There is a SECOND public endpoint for the day's completed scalps:**

    https://pipshed.com/api/g/k7m9p2x4q/scalps/<anything>
    https://pipshed.com/api/g/k7m9p2x4q/scalps/<anything>?date=2026-09-10

Same token, same cache-buster rule. Returns `date`, `total` and `records[]` --
close_time, instrument, direction, entry_price, exit_price, layer_depth,
stack_depth, gross_pnl, instance_id. Omit `?date=` for the current broker day.

**Backfilled records are identifiable by `stack_depth: null`** -- see section 6.

**What the status payload carries, per instance:**

    book.positions[]   ticket, type, price, open_time, open_time_msc,
                       comment, profit
    book.orders[]      ticket, type, price, open_time, open_time_msc, comment
    layers[]           layer_index, side, entry_price, exit_target,
                       has_exit_order, has_exit_position, comment
    l0_pending_*       price and raw comment, or null
    add_pending_*      price and raw comment, or null
    resting_entries_*  count from the BROKER, not the tracker
    recon_failure      on a rejected book: every ticket it saw, with raw
                       comments, plus the offending one
    account_balance, account_equity, intraday_mae   (lease holder only)

**Verified today**: the assistant reproduced the MT5 Trade tab exactly from the

**Why it matters:** five halts today were diagnosed from screenshots, and the

## 3. THE DIAGNOSTIC FIELDS AND WHAT THEY CATCH

| Field | Catches |
|---|---|
| `resting_entries_*` vs pending prices | A duplicate order the EA cannot see. This is what halted an instance on AMBIGUOUS_ADD_LONG while the tracker held one of two. |
| `net_mtm` = 0 with layers > 0 | Phantom layer -- EA holds a layer the broker does not. |
| `has_exit_order` and `has_exit_position` both false | Naked layer. |
| `recon_failure.tickets[]` | What reconstruction saw before rejecting a book. Proved itself on an `I5_SHORT_DUP` -- two positions both labelled `S|L00|ENT`, diagnosed in seconds. |
| `book` vs `layers` | Anything at the broker the EA is not tracking. |
| `open_time_msc` | Ordering two artifacts created in the SAME SECOND. GBPUSD OPT and ALT both filled at 16:42:08 today. |

**Raw comments are read from the broker, never reconstructed.** The point is to
see when the encoding has gone wrong -- a `L03` label on an order whose price
says `L01`.

## 5b. RATIFIED 2026-09-10 EVENING: A POSTGRES ARCHIVE FOR PIPSHED

**Not built. Design settled, ready to spec.**

**The problem it solves.** Every field added today is a SNAPSHOT. All three open
defects in section 4 need HISTORY instead. Specifically: we never established
whether the missing exits' `OrderSend` FAILED or was NEVER ATTEMPTED, and that
distinction is the whole diagnosis. **We log state, not attempts.**

Railway has a **50 GB Postgres, currently unused**. Volume here is trivial --
a few hundred sends a day, twelve heartbeats a minute -- so retention stops
being a design decision.

### Rulings

**Scope, phase 1: SEND LOG and SCALP HISTORY. Snapshots are phase 2.**
Snapshots are largely INFERABLE from a complete event log -- if you know every
send and every fill, the book at any moment is derivable. They are convenience,
not information. Do not let snapshot plumbing delay the send log, which
addresses defects that are actually bleeding.

**Isolation: Redis is operational truth, Postgres is an asynchronous shadow.**
Absolute. `/api/telemetry/push` must NEVER fail because the archive is down --
the EA would see POST failures and the dashboard would go dark for a storage
problem, which is strictly worse than today.

  Pattern: receive the POST, write Redis, return 200 immediately, then
  `RPUSH` the payload to a Redis queue. A SEPARATE worker drains that queue into
  Postgres in batches. If Postgres is down the list backs up and drains later.

  **This is better than "write Postgres and swallow the error"**, which was the
  first proposal -- that loses data during an outage; the queue does not.

**Transport: a SEPARATE endpoint, `/api/telemetry/action`. NOT the heartbeat.**

  The decisive argument is lifecycle, not size: **the heartbeat runs on a timer,
  and if the EA dies between beats you lose the event that killed it.** For a
  diagnostic log that is exactly backwards -- the last event before a failure is
  the one most needed.

  Also: the heartbeat is already ~13 KB at cap and splits across three journal
  lines. A volatile minute of retries would shatter it.

  EA side: push to a local array at `Grind_OrderSendCounted` -- the single choke
  point that already exists -- and flush on a short timer, off the tick path.

**Schema: DISTINCT TABLES, normalised. Not one `events` table with a type
column.** The entire point of Postgres here is queryability. A single table
forces `WHERE payload->>'type' = 'OrderSend'` when you are debugging at 3am.

    send_logs       time_msc, instance, action, order type, price, comment,
                    retcode, resulting ticket, ok
    scalp_history   the nine fields already defined, durable and queryable
                    across days rather than subject to Redis list trimming
    book_snapshots  phase 2, JSONB payload

### Also on the action endpoint

**Config dumps on attach and detach.** The `fxgrind CONFIG ...` line already
prints all twenty inputs plus `symbol=` at `OnInit`, and `fxgrind deinit
reason=N` on teardown. Both go to the journal and nowhere else.

Sending them as events gives the fleet's CONFIGURATION HISTORY -- what was
attached, when, with what geometry, on which symbol.

Three things it catches:
  - **Wrong-chart attach.** A EURGBP preset on a GBPUSD chart shows as a
    `symbol=` that disagrees with the instance name. This happened tonight and
    was caught by eye.
  - **Reload timing.** Whether a compile actually took effect, which mattered
    repeatedly today.
  - **Configuration drift** -- an instance running geometry that does not match
    its preset file is currently invisible.

Same transport, different event type. Spec the endpoint for both from the start.

### Raw log lines -- FILTERED, not wholesale

Do NOT ship the journal whole. Yesterday's Experts log was **125 MB** with
`InpVerboseLog=true` across twelve instances, and it TRUNCATES at 4096 chars --
so archiving heartbeat lines preserves the truncation, not the data, while the
structured payload already arrives intact.

Ship only what has no schema: `ERROR`, `WARN` and `CRITICAL` lines. That is
perhaps 1% of the volume and nearly all of the diagnostic value.

**Once this exists, `InpVerboseLog` can go back to false** -- the diagnostic
value moves to Postgres and the VPS stops accumulating a 125 MB daily file.

### Retention -- PER TABLE, not one global rule

    send_logs       14 days   -- for diagnosing what just happened
    log_lines       14 days   -- same
    scalp_history   KEEP      -- the performance record, and tiny: 27 rows
                                 yesterday, so a year is ~10k rows. Cycle 2's
                                 A/B results live here.
    config_events   KEEP      -- rare, small, and "what geometry was EURGBP ALT
                                 running in September" is a real question
    book_snapshots  14 days   -- phase 2

A nightly `DELETE WHERE time < now() - interval '14 days'` is sufficient at this
volume. Partitioning by day is cleaner but more setup. **The job has to actually
run** -- design retention in, do not retrofit it.

### Sequence

Three independent pieces. **Start with pipshed** -- the EA cannot send anywhere
until the endpoint exists, and the queue-and-worker is testable with curl before
any EA change.

  1. Railway provisioning, migrations, distinct tables
  2. pipshed: `/api/telemetry/action`, Redis queue, drain worker
  3. EA: local array at the send choke point, flush on a short timer

## 6. THE SCALP BACKFILL SCRIPT

`scripts/backfill_scalp_closed.py`, committed. Replays scalps from a deal dump
into the history panel.

Used today to recover the 14 missing events. **Dry run by default**; `--post`
to write. Dedups on `(instance_id, close_time)` against `today_scalps`.

Three traps it handles, all of which would fail silently:

**CloseBy splits P&L across TWO `OUT_BY` deals** -- the broker books the profit
on one and leaves the other at zero. Reading one row is a coin flip. Sum both.

**MT5 CSV dates use PERIODS** -- `YYYY.MM.DD` -- and `fromisoformat` throws.

**`stack_depth` is emitted as `null`.** A single-day dump lacks the starting
state, so any concurrent-open count is guesswork. Null renders as an em-dash;
a `-1` sentinel would render as a number someone later trusts.

**Cloudflare blocks Python-urllib's default User-Agent with error 1010.** The
script sends `fxmatrix-backfill/1.0`. Any future script hitting pipshed needs
the same.

## 7. DEPLOYMENT TRAPS

**Restart the terminal when switching accounts.** GlobalVariables are
TERMINAL-scoped. A new account inherited `GRIND_DAILY_API_COUNT` at 41,576
against a 2,000/day limit and raised `WARN_API_SOFT_LIMIT` immediately.

**`deploy.ps1` does NOT copy presets.** Separate copy to `MQL5\Presets`, then
read one back to verify.

**`deploy.ps1` does not compile either.** It copies files; only F7 in
MetaEditor reloads the EA. This cost an hour today -- the book was `null`
because the VPS had the code but was running the old binary.

**Check `symbol=` in the config dump.** A EURGBP preset was loaded onto a
GBPUSD chart and placed orders before it was caught.

**pipshed has TWO gates, not one.** `_summarize_grind_instance_state()` builds
the card and `_PUBLIC_GRIND_INSTANCE_KEYS` filters the response. Adding a field
to the whitelist alone leaves it null -- `book` was invisible for an hour
because of exactly this.

## 10. A FUTURE DATA SOURCE: PER-POSITION MAE

The FTMO app shows MAE and MFE per position, in pips. Worth noting as a data
source, not a task.

**MFE is useless here, by construction.** The exit is a limit that fills exactly
when price reaches it, so for a closed position MFE IS the exit distance. It
cannot tell you whether a wider exit would have captured more.

**MAE is the useful half**, and it is genuinely independent: a layer can go 40
pips against you and still come back to exit at +5. The exit distance says
nothing about it.

What it would answer that nothing currently can: **how much adverse excursion
each geometry endures to earn its scalps.** Two arms banking the same $0.70 per
scalp are NOT equivalent if one averaged 8 pips of drawdown and the other 30.
That is a risk-adjusted comparison the A/B cannot currently make, and it would
matter a great deal at size.

The EA already tracks the opposite edge -- `exit_penetration_pips` and
`exit_touch_revert_count`. MAE per layer would complete the picture.

Caveats: FTMO computes it from tick data not held locally, so replicating it
means tracking per-position extremes on every tick -- cheap, but it adds state.
And whether FTMO exposes it via an API rather than only the UI is unchecked;
scraping would be fragile.
