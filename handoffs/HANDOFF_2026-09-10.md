## 3. THE FOUR DEFECTS OF 2026-09-09, AND WHY THEY MATTER

All four were caught by invariants halting on live flow, not by anyone looking.
All four were **first-time-ever code paths**.

**(1) Stale add label.** `Grind_EnsureAddNext` derived the layer index from
array depth, but the resting order keeps whatever comment label it was born with
and MQL5 cannot rewrite a comment. When CloseBy unwinds let ladders shrink for
the first time, labels went stale. Fixed with idempotent reconciliation --
compare the resting label against current depth every tick, remove on mismatch.

**(2) Invariant and reconciler targeting the same condition.** I8 halted on
exactly the state the reconciler was built to heal, so the EA stopped before the
fix could run. **The reconciler had never executed in production.** Narrowed I8
to structural corruption only.

**(3) Tracker orphaning.** `grind_engine.mqh:493` cleared
`add_pending_ticket` when a side unwound to flat -- WITHOUT cancelling the
order. The next add was then placed against an empty tracker, producing two
resting entries with the same label. The EA could not see the duplicate.
Fixed by deleting the clear and letting the reconciler handle it.

**(4) Phantom layers.** A layer survived its own close. `invariant_ok` stayed
true because a phantom layer with a phantom exit is internally self-consistent.
**Nothing asserts that a layer's position still exists at the broker.** Cleared
by a reload; the underlying fix is the layer reconciler, still unbuilt (see 6).

**The common cause:** the layer table is maintained by incremental mutation and
nothing continuously checks it against the broker. Reconstruction is the ONLY
code that treats the broker as authoritative -- which is why recompiling fixes
everything.

**General lesson, recorded in ADR-125:** a code path that has never run is not a
path that works. Four this week -- the CloseBy derivation, the depth-0
reconciler, the phantom-layer close, and the CAS lock bootstrap.

## 4. THE SIMULATOR HAD NO LAYER CAP. THIS INVALIDATED THE ORIGINAL GEOMETRY.

**Found 2026-09-10 by accident, while investigating something else.**

`grid_sim_v7_real_signal.py` recorded `max_layers` as an OUTPUT -- a high-water
mark -- and never enforced it. **Every sweep ever run was unbounded**, including
`ac19a9f_confirm`, which selected the live geometry.

Depth reached by sweep:

    a2b9920_cal_shape     med 6    max 8
    precise_n200          med 7    max 7
    ac19a9f_confirm       med 24   max 61     <-- selected the live geometry
    ring_shape_v1         med 29   max 92

Production caps at 12 and 8.

**The ranking was confounded, not merely inflated.** On GBPUSD the P&L ordering
WAS the depth ordering -- width 3 reached 49-54 layers and won; width 7 reached
21-23 and lost. The sweep did not find that tighter geometry harvests better; it
found that tighter geometry stacks more inventory in a simulator that allows it.

**And the gates were measured uncapped too.** Width 3 was disqualified at 32-68%
Gate A breach -- from ladders 49 to 61 deep. **Capped, every single gate breach
vanished: 0% across all pairs and cells.** The disqualification that shaped the
original selection was an artifact.

Cap now enforced per pair from `sim_costs`, raising if a pair has none.

## 5. LIVE OUTRANKS SIMULATION. THIS IS RATIFIED.

The capped re-sweep prefers the TIGHTER exit on two of three pairs. The live A/B
found the WIDER exit won on every measure. **They disagree, and live wins.**

Live P&L is terminal `DEAL_PROFIT` plus swap plus commission -- every cost is
already inside the number. Nothing to model.

The simulator has four known divergences, and one of them explains the
disagreement directly:

1. **Single-sided.** It latches `filled_dir` and runs one ladder; production runs
   both. This understates CHOP HARVEST -- exactly where a wider exit benefits,
   since it holds through oscillations a tighter exit banks out of.
2. Touch-fill, no adverse selection -- a documented ceiling.
3. Brownian bridge between bars, not real ticks.
4. No layer cap until 2026-09-10.

**The single-sided model is correct for RISK** -- price cannot run 500 pips up
and 500 down at once, so one ladder stacking IS the worst case. It is wrong for
HARVEST. That is the safe direction to be wrong in.

**The sweep's proper role is pairs and periods with no live data.** Where real
fills exist, they decide.

## 6. WHAT IS NOT BUILT

**Layer reconciler (the phantom-layer fix).** Ratified design: each tick, verify
every layer's `position_ticket` still selects at the broker; remove it if not.
Same idempotent shape as the add reconciler. **Prerequisite complete** -- the
layer index is now intrinsic, so purging a middle layer no longer corrupts
identity. NOT started.

**Order purgatory / virtualisation.** Ratified since 2026-09-08 and now
URGENT-ish. Twelve instances reserve up to **~272 pending orders against FTMO's
200 limit** in the absolute worst case (all pairs at full cap simultaneously).
Unlikely but not impossible -- these currencies are not independent.

**Before sizing that work, measure actual peak occupancy from the Trade tab.**
If the fleet peaks at 90, purgatory is unhurried; at 180 it is urgent. Real
numbers beat a guess for setting the threshold.

**Failure mode if the limit is hit:** the broker rejects new orders and the EA
sees an `OrderSend` failure, not a clean cap block. Whether that halts, retries
or logs is UNVERIFIED. Worth knowing before it happens.

**Pacing gate (`MinLayerIntervalSeconds = 300`).** Ratified, deliberately NOT in
this cycle -- an unpaced baseline is needed to measure what pacing costs or
saves. At 300s = one M5 bar. Shorter values were considered and rejected: 60s
permits multiple adds per bar, which on a 5-pip grid is barely a gate.

**Price staleness in the deadband path.** A resting add can hold a correct label
with a price computed against a since-moved anchor, if the difference falls
inside the 4-pip deadband. Reported by Cursor, unaddressed.

**Wider audit for incremental-mutation patterns.** Ratified: the CloseBy queue
and the deal dedup array are the next suspects for the same class of drift.

## 7. TELEMETRY -- REBUILT 2026-09-10

**Per-layer detail now in the heartbeat.** Every layer reports `layer_index`,
`side`, `entry_price`, `exit_target`, `has_exit_order`, `has_exit_position`.
Plus `l0_pending_*`, `add_pending_*`, and `resting_entries_*`.

**Tickets are deliberately NOT emitted** -- the status endpoint is public.

**`resting_entries_*` is counted from the BROKER**, not the tracker, and is a
drift detector. pipshed flags drift when it disagrees with
`(l0_pending present) + (add_pending present)`. That is the exact signature of
defect (3), which was invisible to the EA.

**Worst case payload at cap: ~3,748 chars against MQL5's 4,096 `Print` limit.**
348 to spare. The journal splits into two lines when it would exceed; the POST
is never affected.

**Scalp events.** fxgrind now POSTs `scalp_closed` on CloseBy completion --
queued FIFO (max 64, drop-oldest) and drained from `OnTimer`. **No `WebRequest`
on the deal path**, which is synchronous in MQL5 and would freeze the tick.
Dedup guard: only the ENTRY position's OUT_BY completes a scalp.

**pipshed:** two ring sections, v2 surface removed, Arm A / Arm B labels with
slot shown secondarily, layer detail rendered, scalp panel retained and
relabelled. ~293 net lines removed.

## 8. DEPLOYMENT TRAPS LEARNED THE HARD WAY

**Restart the terminal when switching accounts.** GlobalVariables are
TERMINAL-scoped, not account-scoped. The new account inherited
`GRIND_DAILY_API_COUNT` at **41,576** against a 2,000/day limit, and the EA
raised `WARN_API_SOFT_LIMIT` immediately. A restart clears the temp namespace.

**`deploy.ps1` does NOT copy presets.** They need a separate copy to
`MQL5\Presets`. Verify by reading one back after copying.

**Check `symbol=` in the config dump.** A EURGBP preset was loaded onto a GBPUSD
chart tonight and placed orders before it was caught. The dump prints the symbol
alongside the magic -- that line is the check.

**The CAS lock needed a manual GlobalVariable** on a fresh terminal. FIXED --
`GlobalVariableTemp` now bootstraps it atomically. Verified in production:
deleted the key, it reappeared at 0.0 with no CAS timeouts.
